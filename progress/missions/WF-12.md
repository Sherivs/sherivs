- WF-01 to WF-07 gave the tables, the append-only guards on `wf_run_event`, `wf_approval_decision` and

  reused. WF-12 only reads its tenant and category holds and refuses to purge while one is active.
- No limits table, wallet cap, purge function or limits screen existed. ADR-124, issue #470 and migration
  `20261117000960` were free (checked across all open PRs; `..000950` is WF-08, `..001000` is used by #448,

## Review round 1: BLOCKING B1 and notes (20 Nov 2026)

Review of head `53b3de9` found that the migration revoked only `PUBLIC, anon, authenticated`, as WF-03/05/06/07/08
also do for `service_role`. Under Supabase default privileges (`ALTER DEFAULT PRIVILEGES ... GRANT ALL ... TO anon,
authenticated, service_role` for the migrator) the service role could call `wf_retention_pass` and
`wf_retention_execute` directly (no legal hold, dry run, floor or opt-in), update `wf_action_spend_rate`, insert
`wf_org_limits` and delete `wf_quota_denial`. The sim database did not apply those defaults to objects made by
`sim_migrator`, so my harness and CI could not see it. I reproduced it: the new harness fails against the old
migration on a database with the defaults in force.

Fixed in new commits on the same branch:

- B1: every function and table is revoked from `PUBLIC, anon, authenticated, service_role`. Granted back: EXECUTE
  on nine functions (`wf_limits_get`, `wf_limits_update`, `wf_retention_run_manual`, `wf_retention_run_scheduled`,
  `wf_quota_check_action`, `wf_quota_runs_exceeded`, `wf_quota_note_denial`, `wf_block_draft_dispatch`,
  `wf_approved_drafts_ready`) to `service_role`; SELECT on the four tables to `service_role` and on three of them to
  `authenticated`. All writes go through the definer functions. The header text is corrected. Note: the review
  said seven server-called functions; the code needs nine (two more are the sweep's parking calls added for note 6).
- Harness and CI: the WF-12 harness reads the exact ACLs from the catalog and tries the direct calls as
  `service_role`. New `tests/integration/wf12-default-privileges.local.sql` holds an exact allow-list of the
  `wf_*` non-trigger functions `service_role` may execute. A new CI step copies the migrated database, rolls back
  WF-12 and WF-08, sets the default privileges for the migrator, re-applies both and runs the WF-08, WF-12 and
  allow-list checks.
- WF-07/WF-08 and earlier: under default privileges only nine WF-01 trigger functions (`wf_append_only`,
  `wf_approval_guard`, `wf_audit_row`, `wf_definition_guard`, `wf_guard_row`, `wf_run_guard`,
  `wf_step_run_guard`, `wf_trigger_binding_guard`, `wf_version_guard`) are executable by `service_role`. They
  return `trigger` and cannot be called as functions. No WF-03/05/06/07/08 function or table is exposed. I did not
  change those migrations. Only WF-12 (17 functions and 4 tables) was exposed.
- Note 1: a purge needs a dry run that is same-org, completed, under 24 hours old, made with the windows now in
  force, and not used before (`dry_run_id`, a unique index, the retention lock).
- Note 3: the scheduled purge isolates each organization: a failure rolls back that organization only, is
  returned as `failed` with SQLSTATE only, audited `workflow.retention.failed`, and retried on the next call.
- Note 4: the quota-counted triggers set `created_at := now()`, and an executed record's `created_at` and
  `cost_kobo` cannot be updated.
- Note 6: an approved SMS or WhatsApp draft whose rate is undecided (or whose kind is unknown) is parked: one
  `draft.dispatch_blocked` event with the code, off the sweep's list for 24 hours, then checked again. It is not
  a terminal status, because that needs a new draft status (founder decision below).
- Notes 2 and 5: the text of these two notes was not included in the message I received, so I did not change
  anything for them and cannot say they are addressed. Please resend them. (ADR-124 was not updated for them.)

## Not verified

- The screen in a browser (type-checked, linted, bundle-checked, covered by unit tests of its data layer;
  not rendered; no accessibility audit).
- A hosted Supabase, including PostgREST exposure of the new functions. PostgreSQL 17 is covered only by CI.
- Real wallet balances and a real SMS or WhatsApp price. The cost and wallet-balance checks run against a
  fixture rate of 500 kobo set inside the harness transaction; no real rate exists.
- Legal basis for every retention default and minimum (education records, financial approval evidence,
  data-protection law of the deployment country). They are engineering defaults.
- The scheduled purge in a real cron: the route is unit-tested and the SQL function is harness-tested, but the
  Cloudflare worker does not call it and no end-to-end scheduled run was made.
- Concurrency: two sessions inserting against a quota at the same instant (an advisory lock per organization
  serializes the count and insert; no two-session test was written), and a purge running while a run resumes.
- Large backlogs and load: a pass is capped at 5,000 rows per class (tested with 5,001); no timing at
  production scale, no index review beyond the existing ones.
- The e2e's "finished" runs: the fixture's follow-up step is an unassigned task that waits for a person, so
  the e2e marks org B's runs finished by hand (triggers skipped) before aging them. The harness covers
  purge rules against the real states.
- `wf05-event-e2e` could not run in my local database (it needs a seeded synthetic school). WF-05 is untouched
  and its harness passes; CI runs it.
- Live delivery: refused everywhere; no live path was exercised.

## Founder decisions needed

   `wf_action_spend_rate` and replace `wf_wallet_cap_ceiling_kobo()`; nothing else changes.
2. Retention defaults and minimums (outbox 90/30, drafts 180/90, events 180/90, runs 365/180, passkey records
   365/90 days) and the 2555-day (seven-year) approval-evidence default (minimum 730). Legal basis UNVERIFIED.
3. Quota defaults (500 runs a day, 100 steps, 200 pending drafts, email 100, in-app/task/wait 300,
   webhook 60 an hour) and the zero default for SMS and WhatsApp.
4. Any active M12 tenant or category legal hold blocks every workflow purge for that organization. Confirm,
   or say which categories may apply.
5. Old inbound events lose their dedupe keys after the event window. Confirm the window is long enough for
   every source's retry horizon.
6. A dry run reports what is eligible now; chains of rows may need several passes. A pass takes at most 5,000
   rows per class. Confirm.
7. The cron route exists but the Cloudflare worker is not changed. Decide whether and how often to schedule it,
   and which organizations opt in to automatic purge.
8. Migration number `20261117000960` (WF-08 uses `..000950`; `..001000` is used on other branches).
9. `BEGIN`/`COMMIT` inside the migration, as in WF-08. Keep or drop.
10. The WF-07 harness fixture change (sms to email). Confirm that an SMS record being unwritable while the rate
    is undecided is the behaviour you want.
11. Parked drafts (note 6): re-checked once a day rather than made terminal. A terminal state needs a new draft
    status and a WF-06 constraint change. Confirm, or approve that change.
12. A failed organization in the scheduled purge has no log row and is retried on every call until it
    succeeds. Confirm, or ask for a backoff.
