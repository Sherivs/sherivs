## Known Risks

- RLS here is the TENANT boundary only; the in-tenant sharing model
  (private/org/explicit) remains owned by `frontend/src/lib/files/access-policy.ts`
  and the service path. A per-actor SELECT refinement in RLS is a separate
  authorization decision and was deliberately NOT bundled into this migration
  (documented in the header as "Sharing-model layering").
- INSERT/UPDATE are owner-gated (tenant-equality + `owner_ref = auth.uid()`)
  rather than the 20261002000013 exemplar's admin-gated INSERT — a documented
  deviation justified by the file contract (the owner is the lawful writer;
  file-contract.ts: owner "always allowed within its own tenant"), using the
  mh-04 exemplar's actor-pin pattern. Administrative on-behalf uploads must
  run through service-role server functions.
- The `content_ref` CHECK ties the DB shape to the current adapter path
  convention (`tenant/purpose/filename`); any future change to the adapter's
  object-key layout must migrate this constraint in lockstep.
- Migration is unapplied; live posture (relforcerowsecurity, pg_policies,
  catalog grants) is unverified until the coordinator's authorized apply.
- COND-003 (tenant_id text vs uuid) remains unresolved; the substrate uses
  `text` per applied reality, convertible by a follow-up migration.
