## Known Risks / FINDINGS (documented behavior tested; engine NOT modified)

- **FINDING F-1 — no `revoked` identity lifecycle state.**
  `IdentityLifecycleState` models `suspended`/`deleted`/`archived` but has
  no distinct `revoked` state; identity revocation must be expressed as
  `deleted`/`archived`. Both fail closed here, so the gap is semantic, not
  exploitable through the engine — but phase-02 lifecycle vocabulary and
  the engine's gate should be reconciled by the engine owner.
- **FINDING F-2 — no credential/session/delegation inputs to `authorize()`.**
  A revoked credential, expired session, or revoked delegation cannot be
  expressed in an `AuthorizationRequest`; the engine accepts
  `req.attributes` but never consults them (proven: revocation data smuggled
  via attributes still ALLOWs a granted request). Enforcement must live
  upstream (session/credential engines) and callers must not treat request
  attributes as a policy channel. Consistent with the MISSION-R-22 boundary
  note in `authorization-exhaustive.test.ts`.
- **FINDING F-3 — `abac.now` is trusted at face value.** Per the documented
  contract, a parseable `abac.now` IS the request time: a caller-supplied
  future timestamp re-activates a wall-clock-expired relationship (tested
  ALLOW with `abac.now = 2019` against a 2020-expired grant). The engine
  resolves tenant context server-side but places no such guard on
  `abac.now`; server callers must never forward client-supplied values.
  Hardening candidate for the engine owner.
- **FINDING F-4 — `hasRelationship()` has no request context.** It always
  evaluates expiry against wall clock, so it can disagree with `authorize()`
  under an `abac.now` (proven: `authorize` DENY at `abac.now = 2070` while
  `hasRelationship` reports the same relationship active). Documented in the
  engine header; callers needing request-time semantics must use
  `authorize()`.
