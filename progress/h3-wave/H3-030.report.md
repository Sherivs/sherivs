## Security Validation

Every attack that the guard contains is pinned with a TYPED denial (discriminated
verdict + reason, or typed audit record kind) — verified: `entry_invalidated`,
`stale_epoch`, `ambiguous_epoch`, `no_resolved_epoch`, `invalid_clock`,
`invalid_input`, `invalid_target`, `StaleContextError`, and contract audit kinds
`carry_over_denied_no_policy_grant` / `_cross_tenant` / `_permission`,
`derived_context_denied_cross_tenant`, `derived_context_invalidated`.

Five attacks SUCCEEDED and are recorded as precise FINDINGS (asserted honestly,
NOT fixed — ownership is B-013 / coordinator):

- **F1 — Epoch-identity replay.** Epoch ids are FNV-1a over
  `tenant|userId|role|now`. Replaying the ORIGINAL resolution instant through the
  injected clock while switching back to the identical target mints a new epoch with
  the SAME id; the captured pre-switch scope then passes `assertActive()` /
  `scopeIsActive()` / `validateScope()` across a tenant-b interlude (liveness
  forged). Entry-level consumption remains denied (`entry_invalidated`).
- **F2 — Ledgers not runtime-append-only.** `auditTrail()` and
  `runtimeAuditTrail()` return LIVE mutable arrays of mutable records; an in-process
  hostile holder appended forged records (`runtime_execution_completed`,
  `switch_applied`) and rewrote an honest record's `detail` (§29 append-only is
  type-level only).
- **F3 — Cross-tenant smuggling via shallow-frozen scope (highest severity).**
  `withFreshContext` freezes only the entries ARRAY; entry objects are live
  references into the guard's canonical state. A tenant-a callback rewrote an
  entry's `tenantRef` to `tenant-b`, rode the audited carry-over path with a grant
  now "consistent" with the mutated truth, and the tenant-a package
  (`pkg:tenant-a-alpha`) crossed into the tenant-b epoch where guarded consumption
  is ALLOWED — a Constitution §13 bypass.
- **F4 — Audit-detail injection.** The Zod boundary validates only non-emptiness;
  attacker-controlled operation text (including newlines/fake audit lines) flows
  verbatim into ledger `detail` fields (log forging).
- **F5 — Scope over-grant.** `withFreshContext` probes only DECLARED entryIds but
  issues a scope exposing ALL active derived entries (`entryIds: []` still yields
  every entry) — least-privilege violation and the natural delivery vehicle for F3.

## Known Risks

- F3 is a real tenant-boundary bypass reachable by any tenant-scoped callback; F1
  enables scope-liveness forgery wherever callers trust `assertActive`/
  `validateScope` for authorization-adjacent decisions. Both warrant coordinator
  escalation to B-013 (fix: freeze entry objects at issuance; salt epoch ids with
  non-replayable state, e.g. a monotonically derived sequence, or compare epochs by
  identity, not id string).
- F2/F4/F5 are integrity/least-privilege findings; no secret material is involved
  anywhere (fixtures use only synthetic refs like `pkg:tenant-a-alpha`).
- The battery asserts current module behavior; if B-013 fixes the findings, the
  FINDING tests will fail loudly and must then be inverted into containment tests
  by the owning team.
