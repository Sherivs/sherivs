## Known Risks

1. **Residual gap — credential availability in CI (the honest core of this mission):** fork pull requests cannot access repository secrets, so the RLS battery exits 2 (BLOCKED) on forks; per-PR canonical posture proof is guaranteed only for same-repo branches. Closing it needs an operator decision (e.g. a restricted read-only deploy credential surfaced via a merge queue) — outside this team's authority; documented in the workflow header and the exit-2/summary messaging.
2. **Lock contention:** path-scoped PR runs enter `canonical-db-batteries` and queue behind (and hold) the canonical lock during their run. Serial-safe but adds latency to PR CI when a live battery is in flight. The sibling design `architecture/campaigns/h3/recovery-ci-wiring.md` (A-008, §3) proposes the invariant-preserving run-level → job-level lock relocation that removes exactly this contention; I deliberately did NOT relocate the lock (my law: keep it intact; removal/relocation is coordinator+ADR territory).
3. **Reconciliation needed with A-008 (coordinator action):** when applying A-008's YAML on top of this change, the RLS job's `if:` "then becomes unconditional" already holds (I added none); the relocation touches only `concurrency` blocks; A-008's `pull_request.paths` list is recovery-scoped and must be UNIONED with this change's RLS-scoped list (not replaced), or one path set will silently disarm the other's PR coverage. This interaction is flagged in the workflow header for one-workflow reconciliation.
4. Same-repo PR runs execute a live read-only canonical probing battery from PR-supplied code (the script comes from the merge ref). Risk is bounded: the script is credential-gated, read-only catalog queries, evidence redacted — but it is the operator's call whether PR-author-controlled battery code should run with repository secrets; a merge-queue-only posture is the conservative alternative.
