# H3-069 Report — Contract Architect, phase 49 Autonomous Economy Engine

Role: Contract Architect (Squad G). Mission: G-069 — Zod-typed, fail-closed,
domain-neutral contracts for the phase-49 substrate surface.

## Implemented

`frontend/src/lib/autonomous-economy/contracts.ts` — a pure, typed CONTRACT
module (no I/O, no vendor imports beyond `zod`, no secrets, no wall-clock
reads, no database, no network) covering the phase-49 substrate declared by
the phase seed (market and exchange rules; settlement orchestration records;
economic governance records):

- **Governed rules** (`marketRuleSchema`, `parseMarketRules`): declared,
  checkable constraints on exchange and settlement with provenance (AGENTS
  §12), monotonic versions, fail-closed retirement (a retired rule must name
  its reason), and a `changeRequiresHumanApproval: z.literal(true)` binding —
  every rule change is an approval-gated action per the phase-49
  `requiresApprovalFor` seed. Set parsing is fail-closed: no partial sets,
  duplicate rule ids rejected, bounded count.
- **Proposal-only economic intelligence** (`economicProposalSchema`,
  `decideProposalRelease`, AGENTS §21, §7, §8): AI economic actions are AI
  proposals — never autonomous execution. Proposal records carry
  `authorizes: z.literal(false)` and `requiresHumanApproval: z.literal(true)`
  as schema-level literals and must cite canonical `basisRefs` (AGENTS §9:
  intelligence is derived, never conjured). The release decision enforces the
  §21 pipeline order — validation `passed`, policy check `allowed`, then a
  VALID human approval — and a positive decision releases the handoff
  downstream without executing anything (this module has no execution
  capability). Malformed and machine-authored approvals fail closed.
- **§36 payment-security settlement instructions**
  (`settlementInstructionSchema`, `parseSettlementBatch`): mandatory
  idempotency key (bounded), structural replay protection
  (`replayProtected: z.literal(true)`, not opt-out; duplicate idempotency
  keys are REJECTED as replay attempts, never absorbed or deduplicated),
  mandatory signature inputs (`signatureEnvelopeSchema`: recognized
  algorithm, key REFERENCE not key material, opaque bounded digest;
  key-material-shaped input rejected — AGENTS §30), mandatory canonical
  ledger record reference (never money truth: balances stay with phase 13 —
  an instruction without a ledger reference is rejected, not defaulted),
  positive integer minor-unit amounts with a hard ceiling, strict currency
  codes, and tenant/owner/counterparty references.
- **Ownership validation** (`ownershipClaimSchema`,
  `validateSettlementOwnership`, AGENTS §36): the claim is parsed here
  (malformed claims fail closed, never defaulted) and tenant AND owner must
  match the instruction exactly — cross-tenant settlement is rejected.
- **Derived-intelligence canonical separation** (`derivedObservationSchema`,
  `requiresHumanReview`, AGENTS §9, §12): derived economic intelligence
  (price suggestions, forecasts, recommendations, insights) is structurally
  non-canonical (`isCanonical: z.literal(false)`) with mandatory basis
  provenance and bounded confidence; sub-floor confidence
  (`MIN_CONFIDENCE_FOR_ACTIONABLE`) flags human review — never silently
  actioned.
- **Append-only audit trail** (`economicAuditEventSchema`,
  `parseAuditTrail`, AGENTS §29, §36): every surface action class has an
  audit event kind; records have no mutable status; trails enforce duplicate-id
  rejection and non-decreasing occurrence order (an append-only trail cannot
  be reordered after the fact).
- **Citable posture constants**: `ECONOMY_BOUNDARY` (the economy orchestrates
  exchange; it never owns money truth — phase 13 ledger, phase 27 listings;
  no economic rule may move value outside the ledger) and
  `PROPOSAL_ONLY_POSTURE` (AGENTS §21).

Composed with platform primitives read-only: the module implements the
boundary declared by
`frontend/src/lib/kernel/phase-contracts/phase-49-autonomous-economy.ts`
(substrates: market and exchange rules, settlement orchestration records,
economic governance records; excludes ledger/payments phase 13, listings
phase 27, enforcement phase 08) without importing or modifying it. No
sibling H3 modules imported.

## Security Validation

- Fail-closed parsing everywhere: malformed input yields a typed failure
  with structured issues; no partial rule sets, batches, or trails escape.
- §21 posture is structural: proposals cannot carry `authorizes: true` or
  `requiresHumanApproval: false`; the release decision stops on any missing
  or negative pipeline step; execution does not exist on this surface.
- §8 enforced: approvals must reference a human identity via the `human:`
  prefix; agent/self references are rejected.
- §36 enforced: idempotency mandatory; replay attempts rejected (never
  absorbed); signatures required with key references only (key-material-
  shaped digests rejected — AGENTS §30); ownership (tenant AND owner)
  validated with cross-tenant rejection; every action class audited;
  money truth never computed or cached here — a settlement without a
  canonical ledger reference is rejected.
- §9/§12 enforced: derived intelligence is non-canonical with mandatory
  provenance; sub-floor confidence routes to human review.
- No secrets handling; nothing secret-shaped accepted, stored, or logged.
- This module owns no enforcement and grants nothing; authorization remains
  with the phases that own it (phase 08 et al.).

## Known Risks

- The module defines contract STRUCTURE and fail-closed semantics only;
  cryptographic signature VERIFICATION, ledger writes, and settlement
  execution belong to the future phase-49 runtime and the owning execution
  surface, which must consume these schemas.
- The `human:` reference prefix distinguishes human from machine-authored
  approvals syntactically; cryptographic proof of principal authenticity
  remains the platform identity layer's responsibility (phase 08).
- The release decision cannot verify that the cited canonical `basisRefs`
  exist; existence and freshness checks belong to the consuming runtime.
- Amount/currency validation is shape-level; ledger reconciliation remains
  with phase 13.
