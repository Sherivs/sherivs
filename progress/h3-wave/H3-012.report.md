# H3-012 — Context Package Auditor (B-012 / J-011) §42 Report

Team: H3-012 · Role: Context Package Auditor · Mission: B-012 (Squad B, J-gap J-011) · Date: 2026-10-03

## Implemented

`frontend/src/lib/context/package-completeness.ts` — a pure Zod checker proving that a
context package carries the full scope statement required by J-011: `memory_scope`,
`data_scope`, `risk_level`, `trace_id` — all present and well-formed.

- `contextPackageSchema` (closed/strict shape) plus per-field schemas: `scopeRecordSchema`
  (`domains`, `max_sensitivity: public|internal|restricted`, `origin: declared|derived`;
  duplicate-free domains, bounded counts/lengths), `riskAssessmentSchema` (`level:
  low|medium|high|critical` + `origin`), `traceIdSchema` (bounded, whitespace-free token —
  accepts the assembler's `ctx-trace-<hex>`, caller correlation ids, UUIDs).
- `checkContextPackageCompleteness(input)` — fail-closed verdict that names exactly which
  fields are MISSING vs present-but-MALFORMED (per-field attribution with path+message);
  never a bare boolean. Non-object inputs and package-level unknown keys are rejected as
  `invalid_shape`.
- `wirePackageFromEnvelope(envelope)` / `checkEnvelopeCompleteness(envelope)` — type-only
  adapter proving that the governed assembler's envelopes (`../context-assembly`, camelCase)
  satisfy the completeness contract; rejected envelopes fail closed with all four fields
  reported missing.

Domain-neutral vocabulary throughout (scope/sensitivity/risk/trace/package — no domain words).
No `any`, no `z.any()`; strict objects so undeclared semantics cannot leak into a scope.

## Audit Findings (read-only, existing context contracts)

1. `frontend/src/lib/context-assembly.ts` (J-011 / V1CAP-023/024) is the owner of the
   four-field scope statement: every `assembled` envelope carries `memoryScope`,
   `dataScope`, `riskLevel`, `traceId`. Undeclared memory scope defaults to an explicitly
   EMPTY derived scope (never a wildcard); declared data-scope ceilings are enforced
   (candidates above the ceiling are excluded as `exceeds_declared_scope`, not silently
   included); risk is derived from surviving sensitivity plus one-step escalation for
   untrusted content, with `critical` reserved for declared risk; trace ids are FNV-1a
   deterministic or caller-supplied. Verified complete by the adapter tests.
2. `frontend/src/lib/context/switch-safety.ts` (J-012 / G-070) binds `traceId` onto every
   context epoch and enforces zero-bleed switching with audited carry-over. FINDING: its
   validation is hand-rolled (`typeof` checks), not Zod-validated; it fails closed, but the
   epoch shape has no schema-level proof. Out of B-012 scope (B-013 owns the switch runtime).
3. `frontend/src/lib/ai-context.ts` (phase-26) owns trust classification and retrieval
   authorization but carries no package-scope fields — the scope statement lives on the
   assembler envelope. No conflict with this mission.
4. GAP CLOSED: prior to this mission no Zod contract proved that the four scope fields are
   present and well-formed — the envelope was assembled as ad-hoc object literals with no
   schema-level completeness proof. This module is that proof.
5. NAMING NOTE: the assembler uses in-process camelCase (`memoryScope`); the wire/mission
   vocabulary is snake_case (`memory_scope`). The adapter keeps both canonical without
   redefining either owner's vocabulary.

## Security Validation

- Fail-closed: missing or malformed fields never yield an `ok` verdict; unknown keys are
  rejected at every level (strict objects), so undeclared semantics cannot leak into a scope.
- Attribution: every failure names field + path + message (Constitution §12/§29 — auditable
  incompleteness), and `trace_id` well-formedness keeps packages correlatable/attributable.
- Tenant/authorization posture unchanged: the checker grants nothing and decides nothing —
  it proves a statement that already exists on the package (§34: UI/schema is not security;
  enforcement stays in the assembler and authorization layer).
- No secrets printed, logged, or written; no git commands; no database/network access.

## Known Risks

- Bounds are policy choices (≤64 domains, ≤128-char tokens/ids); if a legitimate caller
  correlation id exceeds 128 chars it will be judged malformed. Recorded here as an explicit
  contract bound, adjustable by the contract owner (J-011) later.
- `risk_level` structure is validated but its value is not cross-checked against surviving
  content sensitivity (deliberate: declared risk overrides derived risk per J-011; semantic
  re-derivation here would violate the ownership boundary).
- Concurrent-wave note: the adapter's type-only import targets `../context-assembly`, which
  no H3 team owns for edits this wave; if a future wave changes the envelope scope fields,
  the adapter is the single surface to update.
