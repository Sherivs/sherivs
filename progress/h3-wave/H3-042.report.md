## Implemented

- `frontend/src/lib/observability/deployment-gate.ts` — the serving-URL monitoring
  gate contract:
  - typed poll results `ok | degraded | failing`, composed **read-only** with the
    existing `frontend/src/lib/observability/health.ts` contract: `HealthStatus`
    taxonomy, `aggregateStatus` (worst-of), `isHealthStatus` (body validation);
  - `serializeError` from `structured-log` for all failure evidence
    (`Name: message` only — never stack traces or raw payloads);
  - bounded retry/backoff policy: schema-capped `maxAttempts` (≤ 5); transport
    errors and 5xx retry on a capped exponential schedule
    (`min(base × multiplier^(n−2), max)`); 4xx, unexpected 2xx, and — under
    `inspectBody` — invalid health bodies are deterministic and never retried;
  - fail-closed on invalid configuration: a config failing Zod validation, URL
    law, or uniqueness blocks BEFORE the transport is invoked
    (`config: null`, `probes: []`, named reasons);
  - gate verdicts are exactly `PASS | BLOCKED`; only an unambiguous `ok`
    aggregate passes — `degraded` and `failing` both block;
  - secrets law in code: rejected URLs are never echoed into blocked reasons
    (their query/userinfo may carry secrets); monitored URLs must be http/https,
    userinfo-free, query-free, fragment-free (`servingUrlProblem` names each rule);
  - offline-testable by construction: transport, sleep, ISO clock, and
    millisecond clock are all injectable.
- `docs/runbooks/deployment-monitoring-gate.md` — the BLK-3 operational procedure:
  golden questions, what the gate must observe (transport outcome, HTTP status,
  latency budget, optional health body), modes (offline battery vs live
  observation), the verdict/block-semantics table, bounded retry/backoff numbers,
  fail-closed and secrets law, evidence discipline (full gate-result object,
  provenance, two-person rule, append-only honesty), operator procedure, and the
  relationship to the other launch blocks (BLK-2/4/5). Marked GOVERNED NOT
  EXECUTED — no live observation was run by this mission.
- `tests/unit/h3-042-deployment-gate.test.ts` — offline battery (mocked transport
  only): 33 tests covering classification, retry/backoff bounds, body
  composition, 12 invalid-configuration cases (transport never invoked), secrets
  law (no URL/userinfo echo in reasons, no stack traces in evidence), and

## Architecture Impact

- Pure additive observability contract under `frontend/src/lib/observability/`
  (own subdirectory per campaign law §8); domain-neutral vocabulary throughout.
- READ-ONLY composition: imports only existing `./health` and `./structured-log`
  exports; never writes health state; no vendor coupling (transport is an
  injected port, provider-agnostic per AGENTS §24/§25).
- Fail-closed by default at three layers: config validation, per-probe
  classification, and gate aggregation — mirrors the battery exit-code
  discipline used across the wave.
- No tenant boundary crossed: the gate observes public serving URLs only and
  takes no credentials (rejected URLs carrying userinfo/query).

## Security Validation

- Fail-closed matrix proven by test: invalid configuration → BLOCKED with the
  transport never invoked; attempts exhausted → failing; revoked/absent
  credentials are not a gate concept (the gate holds none by design).
- Secrets: no secret values printed/logged/written anywhere; error evidence is
  `Name: message` only; rejected URLs (query `?token=…`, userinfo) are proven
  never to leak into `blockedReasons` (dedicated tests).
- Untrusted-input posture: raw config is Zod-validated; response bodies are
  only read when `inspectBody` is enabled and must satisfy `isHealthStatus`;
  AI/gate output is treated as untrusted — the runbook binds the verdict to a
  human, second-engineer review (AGENTS §21).
- No new attack surface: no network code of its own (transport port), no
  database access, no filesystem access, no environment/secret reads.

## Known Risks

- The gate classifies latency against a single configured budget
  (`degradedLatencyMs`); percentile/SLO-aware latency gates are out of scope for
  V1 (F-051 SLO cards may later refine budgets).
- Transport timeout enforcement is the transport's responsibility (the gate
  passes `requestTimeoutMs` and never waits unbounded, but cannot cancel a
  misbehaving transport itself).
- `BLOCKED` on `degraded` is intentionally strict (fail-closed launch law);
  relief requires a governed human waiver recorded as evidence, not a code path.
