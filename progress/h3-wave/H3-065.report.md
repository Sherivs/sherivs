# H3-065 — §42 Mission Report (G-065, Contract Architect, phase 45 AI Compute Civilization Engine)

## Implemented

Typed, fail-closed, domain-neutral CONTRACT module for the phase-45 substrate
surface: **governed, metered, fail-closed compute-offer clearance** (admission
of compute allocations against registered compute offers).

- `frontend/src/lib/ai-compute/contracts.ts` (pure, no I/O, no vendor imports):
  - `computeOfferDescriptorSchema` — bounded compute-offer declaration
    (capacity ceiling, **mandatory finite positive metering rate** — an
    unmetered offer cannot register, per the phase-45 principle "unmetered
    compute is refused"; explicit residency scope; fail-closed
    `tenantScoped: z.literal(true)` isolation; refs pinned to the canonical
    `compute:` namespace via the kernel manifest-id law).
  - `computeAllocationRequestSchema` — allocation request carrying a gateway
    purpose (§20), workload kind, bounded duration, residency constraint, a
    metering commitment (per-allocation budget + metering key), and §12
    provenance.
  - `computeClearanceContextSchema` — server-resolved context (tenant, offer
    snapshot, metering ledger; §26: caller never supplies these; duplicate
    refs/keys rejected).
  - `decideComputeClearance` — ALLOW/DENY decision function, fail-closed on
    every missing/malformed/unresolvable/cross-tenant input: unknown offer,
    tenant mismatch (§31), non-`available` lifecycle status, unsupported
    workload kind, residency violation, capacity exhaustion, unmetered
    request (unknown metering key), budget exhaustion (per-allocation and
    remaining period budget, with exact ledger-precision cost projection).
  - `ALLOWED_INVOCATION_PATH = "gateway"` — an allowed decision carries
    invocationPath `"gateway"` as a literal the caller cannot set (§20:
    compute allocation never mints a second path to models; the allow branch
    exposes no path field other than the gateway literal).
  - `canTransitionOfferStatus` / `OFFER_STATUS_TRANSITIONS` — phase-45 offer
    lifecycle transition law (registered → validated → available → …;
    retirement terminal).
  - `capacityStatusForTenant` — tenant-scoped capacity-status read
    projection (§27: cross-tenant rows never returned; posture derived,
    never optimistic).
  - `COMPUTE_GATEWAY_PURPOSES` — gateway-purpose vocabulary locked in
    lockstep with `metering/usage-ledger.ts` (read-only platform-primitive
    composition; no sibling H3 module imports).

- `tests/unit/h3-065-ai-compute.test.ts` — 42 offline tests proving the
  semantics above plus vocabulary lockstep (GATEWAY_PURPOSES, kernel manifest
  ids) and module hygiene (no `any`/`z.any`, no I/O/vendor imports, no timers
  or env reads, no secrets/credential-shaped fields, J-037 neutrality token
  list — which is why the surface vocabulary is "clearance", not the domain
  homonym of that word).

## Security Validation

- Fail-closed by construction: unparseable request/context, unknown source,
  unknown offer, cross-tenant offer (§31), non-`available` status,
  unsupported workload kind, residency violation, capacity exhaustion,
  unknown metering key, exhausted per-allocation or period budget — all
  deny with typed reasons; nothing throws or guesses.
- Metering law: offers without an explicit finite positive rate cannot
  register; requests without a resolvable metering key are refused; cost
  projection uses ledger precision and admits exactly at budget boundaries
  without drift.
- §20 encoded structurally: allow decisions carry `invocationPath: "gateway"`
  as a literal; the decision schema rejects any other value and the allow
  branch exposes no caller-settable path field (forged decisions fail
  schema parse).
- §26/§31 proven by test: tenant comes only from the resolved context;
  cross-tenant offers deny and denials never name the foreign tenant;
  capacity-status projection never returns cross-tenant rows.
- Hygiene: no secrets or credential-shaped fields, no vendor imports, no
  I/O, no timers/env reads; J-037 neutrality token sweep passes (module and
  test both).

## Known Risks

- The module is a CONTRACT surface only: enforcement wiring (server
  functions calling `decideComputeClearance`, persistence of offers and
  metering rows) is a later bounded mission per the phase-45 acceptance
  map; the acceptance status remains ARCHITECTURE_DEFINED.
- The metering ledger slice is a per-key cost snapshot supplied by the
  server context; concurrent-allocation races (double-spend within one
  period) must be enforced by the persistence layer (constraints/RLS), not
  by this pure module.
- "admission" is a J-037 strict token, so the surface vocabulary uses
  "clearance"; downstream consumers must map phase-45 prose "admission"
  to `decideComputeClearance`.
