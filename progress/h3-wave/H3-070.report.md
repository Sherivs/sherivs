## Implemented

`frontend/src/lib/human-interface/contracts.ts` — the Zod-typed, fail-closed, domain-neutral contract surface for the phase-50 human loop-closure substrate (per `architecture/phase-50-human-civilization-interface-layer.md` and the phase-50 row of `architecture/phase-completion-status.md`, status `ARCHITECTURE_DEFINED`):

- **Interaction sessions** (`interactionSessionSchema` + `parseInteractionSession`): presentation channels, locale, optional presentation preferences (non-authoritative), lifecycle invariant — only closed sessions (CLOSED/BLOCKED/FAILED) may carry a close time; fail-closed otherwise.
- **Human loop-closure views** (`loopClosureViewSchema`, `parseLoopClosureView`, `humanLoopClosureVerdict`): every stage entry must carry a server attestation; stage entries must walk the canonical loop in order without repeats (cross-record invariant); the loop closes ONLY when every stage is server-attested and the walk spans `intent → action → feedback` — pending/failed/blocked stages, wrong start stage or a walk that never reaches feedback leave the loop OPEN with a typed fail-closed reason. Closure is never presumed.
- **Approval surface as a typed VIEW of server decisions** (`approvalViewSchema`, `parseApprovalView`): display states (`pending/granted/denied/redacted/expired/revoked`) echo server state only; resolution-instant lifecycle invariant (pending views carry `resolvedAt: null`); adversarial guard — any client-authority-shaped key (`client_*authoriz*`, `locally_approved`, `selfGranted`, `ui_*granted*`, …) anywhere in the input fails parsing with reason `client_authority_claim` (AGENTS §34: the UI is not security).
- **The single sanctioned decision echo** (`displayStateForServerDecision`): maps the authorization engine's §16 vocabulary (`AuthorizationDecision`, imported read-only as a type from the platform identity module) to display states; approval views cannot name a server decision any other way.
- **Human response submission** (`approvalResponseSubmissionSchema`, `parseApprovalResponseSubmission`, `submitApprovalResponse`): responder kind is structurally `human` (an AI identity cannot transmit a resolution through the interface, AGENTS §7/§21); the only possible outcome is a receipt `{ status: "submitted_for_server_adjudication", resolutionClaimed: false }` — the interface can never resolve an approval.
- **Observation views** (`observationViewSchema`, `parseObservationView`): `derivation: "view"` literal required — a view can never present itself as canonical truth (AGENTS §9).
- **Explanation views** (`explanationViewSchema`, `parseExplanationView`): why-statement, digest-bound evidence citations (≥1 required — an uncited explanation is not renderable), explained confidence (value + deriving factors + method, never a bare number), alternatives.
- **Control submissions** (`controlRequestSubmissionSchema`, `submitControlRequest`): override/pause/resume/terminate are queued only — receipt `{ status: "queued_for_server_enforcement", effectClaimed: false }`; enforcement is server-side.
- **Consent surfaces** (`consentPromptViewSchema`/`parseConsentPromptView`, `consentSubmissionSchema`/`submitConsentDecision`): prompts are server-attested views; consent decisions are submissions only — receipt `submitted_for_server_recording`, `consentRecorded: false` (consent records are canonical truth the server owns, AGENTS §9).
- **Feedback submissions** (`feedbackSubmissionSchema`, `submitFeedback`): proposals into the loop — receipt `submitted_for_server_processing`, `learningClaimed: false`.

Laws held throughout: pure module (no I/O, no persistence, no wall-clock reads — all instants are parameters), strict TypeScript (no `any`, no `z.any()`, `z.strictObject` everywhere so unknown keys fail), bounded arrays, typed fail-closed parse results (`SurfaceParseResult` with reasons `invalid_shape` / `client_authority_claim` / `cross_record_invariant` / `invalid_responder_kind`), provenance on every surface (AGENTS §12), neutral vocabulary only (J-037), composition limited to platform primitives read-only (`zod`, `AuthorizationDecision` type) — no sibling H3 modules, no vendor imports.

## Security Validation

- **§34 (UI is not security):** no surface schema can represent a client-granted authorization; the authority-claim key guard rejects `client_authorized`/`locally_approved`/`selfGranted`/`ui_granted`-shaped payloads at parse time with a typed reason; `displayStateForServerDecision` is the only path from decision vocabulary to a view state.
- **§7/§21 (AI proposes, humans resolve):** approval response `responderKind` is `z.literal("human")`; an agent-shaped submission fails closed.
- **§9 (canonical truth):** all surfaces carry `derivation: "view"`; receipts structurally cannot claim resolution/recording/enforcement/learning (`resolutionClaimed: false`, `consentRecorded: false`, `effectClaimed: false`, `learningClaimed: false` are non-writable literal types).
- **§12 (provenance):** every view requires a `serverAttestation` (serverRef, tenantId, payloadDigest, recordedAt).
- **§26/§27 posture:** module is presentation-only — no authentication, authorization, tenant resolution or audit responsibility is claimed; it is a typed rendering contract over server decisions, and tenant scoping is validated structurally in every schema.
- No secrets, no network, no database, no git.

## Known Risks

- The substrate is contract-only (`ARCHITECTURE_DEFINED`): no runtime server path yet produces these views; wiring is a later bounded mission (per the phase acceptance record, implementation/runtime evidence is explicitly deferred).
- `explanationViewSchema.confidence.derivedFrom` is `z.array(z.string()).min(1)` — open-vocabulary factor names keep the module domain-neutral; a closed factor taxonomy would need a cross-phase platform primitive to avoid duplication.
- The client-authority key guard is pattern-based (like the G-054 chain-of-thought guard); a future runtime should also enforce the invariant server-side.
