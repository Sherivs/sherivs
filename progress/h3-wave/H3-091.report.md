## Implemented

`frontend/src/lib/payments/legacy-tier-reconciliation.ts` — the legacy
subscription-tier → neutral entitlement mapping, pure, typed, fail-closed:

- **Authored decision table** `LEGACY_TIER_PLAN_MAP`: each recognized legacy
  tier name (`trial`, `starter`, `growth`, `professional`, `enterprise`)
  maps to a domain-neutral plan (`planId`, `planClass`, `capacityClass`,
  closed `capabilities` set, §12 provenance). 19 neutral capability classes
  (J-037 vocabulary only — the legacy catalog's domain feature-key matrix is
  never named in the module).
- **`reconcileLegacyTierPlan`** — raw legacy tier value → typed
  reconciliation decision. Case/whitespace variants resolve to the SAME tier
  only; missing → `missing_tier`, unknown → `unrecognized_tier`, both
  deny-with-reason. Never coerces (contrast: the legacy catalog's `getTier`
  fails OPEN, silently granting the trial plan to unknown values — recorded
  as a finding below and pinned by test).
- **`neutralEntitlementsForTier(tenantId, tier)`** — TenantId-keyed
  entitlement records for all 19 capability classes in declared order,
  frozen, provenance-stamped. Unrecognized/missing tier ⇒ every record
  denies with `fail-closed-no-recognized-tier` marker; empty tenant id
  throws (caller defect, mirrors `tier-entitlements.ts`).
- **`isNeutralCapabilityEntitled`** — single-capability probe; denies on
  unresolvable tier AND on a runtime capability outside the closed class
  set (defends against type-system bypass).
- **`reconcileLegacyTierNameSet`** — bulk census reconciliation for drift
  detection: classifies every observed value; defects surface in
  `unrecognized`, nothing dropped or absorbed.
- **Zod-validated contracts** (zod v4, `strictObject`): plan schema,
  entitlement schema, discriminated-union reconciliation schema; the
  authored table is parsed at module import — a drifted table fails at
  import time (fail-closed authoring).
- **Design boundary**: the module deliberately does NOT import
  `../subscription-tiers.ts` — importing it would pull domain vocabulary
  into the neutral plane. Grounding against the live catalog is done by the
  test (which owns the domain vocabulary), so catalog drift fails the test,
  not silently in production.

## Architecture Impact

- Adds the neutral entitlement plane (J-037) beside — not replacing —
  `payments/tier-entitlements.ts` (which stays the legacy feature-key
  translation) and `payments/legacy-reconciliation.ts` (money-row
  reconciliation). No existing module modified; no new dependencies
  (zod already present); package.json untouched.
- Authority boundary preserved (Constitution §16): the module answers the
  pricing/contract fact "what does this tenant's plan entitle?", never the
  access decision "may THIS actor use this capability?" — that remains the
  canonical feature-access surface.
- Capacity NUMBERS (seat/storage ceilings) are intentionally NOT duplicated;
  only the capacity CLASS is mapped (the test proves the class ordering
  matches the catalog's numeric ordering), keeping the catalog the single
  numeric authority.

## Security Validation

- Fail-closed everywhere: no default plan grant on ambiguity; unknown tier,
  missing tier, unknown capability, and empty tenant all deny/throw.
- Normalization cannot escalate: case/trim only maps onto the identical tier
  of a static, frozen, import-validated table.
- No I/O, no network, no database, no clock reads, no mutation of inputs;
  all outputs deeply frozen; provenance stamped per §12.
- Reason strings truncate echoed raw tier values to 64 chars (log-hygiene);
  no secret values exist in this module and none were printed.
- The UI-is-not-security rule respected: this is a contract/pricing fact
  plane only; enforcement of actual access stays server-side in the
  canonical feature-access surface.

## Known Risks

- **FINDING (pre-existing, read-only)**: `frontend/src/lib/subscription-tiers.ts`
  `getTier()` fails OPEN — any unknown tier silently becomes `trial`
  (granting a plan to a defective record). Not fixed here (file is outside
  my ownership); `tier-entitlements.ts` inherits this via `getTier`.
  Recommend a follow-up mission to make unknown tiers deny there too.
- **FINDING (grounded)**: the professional tier's `white_label` and
  `custom_domain` are FALSE in the live catalog (only `remove_branding` is
  true) — the initial mapping assumed branding was premium-wide and the
  grounding test caught it; the mapping now models `branding_removal`
  (professional+) separately from `platform_branding` (enterprise only).
  Worth knowing when pricing/entitlement surfaces consume this plane.
- Capability-class granularity is coarser than the legacy matrix (by design):
  within-class breadth (which payment rails, which channels) is not exposed
  here; consumers needing that must still resolve via
  `payments/tier-entitlements.ts` / the catalog.
- If the legacy catalog later ADDS a tier, `LEGACY_TIER_NAMES` won't include
  it and it will classify as `unrecognized_tier` (fail closed) and the test
  set-equality check will fail — deliberate drift detection, but the mapping
  table must then be extended by an owning mission.
