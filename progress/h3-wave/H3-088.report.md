# H3-088 Report — Posture Validation Engineer (Squad H)

## Implemented

Mission H-088: author `tests/unit/h3-088-posture-validation.test.ts`, an offline
edge-case suite for the battery's posture-parsing pure functions, imported
READ-ONLY from `scripts/verify-rls-isolation-battery.mjs` (plain module import —
no execution, no I/O against the repo, no credentials, never exits).

Coverage (84 tests across 9 describe blocks):

1. **Registry constants** — `TABLE_POSTURES` is exactly the two canonical
   postures; `POSTURE_FILE_PATTERN` matches only `rls-table-postures-*.json`
   (rejects `.bak`, bare `postures.json`); `PROBE_PLACEHOLDERS` is the exact
   six-token set (`$TENANT_A`, `$TENANT_B`, `$ACTOR_A_ID`, `$ACTOR_B_ID`,
   `$ACTOR_C_ID`, `$RUN_ID`).
2. **Merge order semantics** — `resolvePostureRegistry`: empty files →
   `fallbackUsed` with `postureSource: "builtin-canonical"` on every table;
   posture-JSON entries override builtin tables in place (builtin slot order
   preserved, `postureSource`/`source` re-stamped); brand-new tables are
   appended and reported in `added`; `overridden` follows file application
   order; a custom injected fallback registry is honored; merging never
   mutates `BUILTIN_TABLE_POSTURES`.
3. **Duplicate-table rejection** — same-file duplicates, cross-file
   duplicates, duplicate-of-an-already-overridden builtin, re-declaration of
   an added table, and duplicates expressed through the `table`/`name` alias
   pair are all rejected ("a security posture must have exactly one source of
   truth"), with the two citing file names in the error.
4. **File-level shapes** (`parsePostureFile`) — bare arrays, `{tables: []}`
   and `{postures: []}` sibling shapes accepted; non-JSON, bare scalars,
   non-array `tables`/`postures`, `{}`, and non-object entries fail closed
   with the file name in the error.
5. **Entry-level strictness** (`validatePostureEntry`) — `table`/`name`
   aliases accepted, conflicting aliases rejected; table names must match the
   plain SQL-identifier pattern; unknown posture values and missing posture
   rejected; malformed `source`/`sourceMigration` rejected, alias normalized;
   default provenance `posture-file:<name>` (AGENTS §12) plus `postureSource`
   stamp; `policies` array-ness, empty/ill-typed policy entries, declaration
   objects normalized to names with `policyDeclarations` preserved; repeated
   policy names rejected; `tenantColumn` identifier-checked; `forceRls`
   boolean-checked and defaulted (true for policy-backed, false for
   zero-policy).
6. **Zero-policy vs policy-backed expectation mismatches** — zero-policy with
   `policies` rejected ("zero policies IS the posture"); zero-policy with
   `forceRls: true` rejected; policy-backed without non-empty `policies`,
   without `tenantColumn`, or with `forceRls: false` rejected; `privileges`
   role shapes validated for exactly `anon`/`authenticated`/`public`/
   `service_role`; policy-backed empty `privileges.authenticated` rejected
   (the policies must be the operative row gate) while zero-policy tolerates
   it; unknown extra privilege roles pass through unvalidated.
7. **Invalid recipe shapes (§4.4)** — probe recipe on zero-policy rejected;
   partial declarations (`probeSeedRows` XOR `probeInsertPayload`) rejected;
   empty/null/array/scalar seeds and payloads rejected; `probeAuxTables`
   requires the full policy-backed recipe and well-formed `cg_`-prefixed aux
   specs; a fully-formed recipe validates and passes through with
   `resolveProbeStage` → `"recipe"`.
8. **Unknown-field strictness** — unknown fields (rationale-like prose,
   `appendOnly`, `absentPolicies`, nested objects) pass through untouched as
   provenance and survive registry merge, while KNOWN fields keep their
   strictness regardless of unknown riders. **Rationale-string independence**:
   the suite is fully synthetic — it never reads
   `scripts/verification/rls-table-postures-*.json` — so Squad D's
   adjudications and J-099's final-batch rationale merge cannot perturb it
   (no assertion depends on any rationale content).
9. **Token replacement** (`substituteProbeValue`) — exact-match-only
   substitution; no partial/embedded substitution (`"$TENANT_A-suffix"`,
   `"$TENANT_A$TENANT_B"`, trailing space, case variants all preserved);
   undeclared placeholders untouched; recursive through objects and arrays;
   object KEYS never substituted; non-string primitives untouched;
   prototype-pollution-safe (`toString`, `constructor`,
   `hasOwnProperty` are NOT treated as context).
10. **Probe SQL construction** (`sqlLiteral`, `buildProbeSeedSql`) — NULL /
    finite numbers / booleans / defensively apostrophe-escaped strings;
    JSON rendering for objects/arrays and non-finite numbers (`NaN` →
    `'null'`); unsafe table or column names rejected before SQL assembly;
    empty rows array yields empty SQL; per-row column lists rendered exactly.
11. **Probe stage resolution** (`resolveProbeStage`) — zero-policy →
    `not-applicable` even with recipe fields present; neutral-membership
    builtin stage for `cg_org_membership`/`cg_role_assignment`/`cg_role_grant`;
    explicit recipe beats the builtin; partial recipes and empty seeds /
    null payloads → `undeclared` (never a silent pass).
12. **`loadPostureRegistry` offline wrapper** — missing directory falls back
    to builtin; a temp directory (os.tmpdir, cleaned up in `afterAll`) proves
    only `rls-table-postures-*.json` files are read, sorted by name, merged in
    that order, non-matching files ignored, and a malformed discovered file
    fails closed citing its name.

## Security Validation

- The suite itself is the security validation: it proves the posture parser
  fails closed on every malformed shape that could weaken or ambiguate an RLS
  check (unknown posture values, duplicate sources of truth, policy-less
  FORCE expectations, empty `authenticated` privilege gates on policy-backed
  tables, partial probe recipes, unsafe SQL identifiers).

  (module import path only; the CLI credential gate is never exercised).
- No test was weakened, skipped, or made conditional on environment.

## Known Risks

- The suite asserts exact error-message fragments and structural behaviors of
  the battery's exported functions; if the battery's messages are reworded,
  the affected assertions will need a mechanical fragment update. This is by
  design (the messages are the battery's contract with operators).
- `expectInvalid` invokes each failing function twice (once via
  `toThrow`, once to capture the message). All covered functions are pure and
  throw-fast, so this is side-effect-free.
- J-099's rationale merge touches posture JSON fields the suite intentionally
  ignores (synthetic entries only), so no ordering coupling exists.
