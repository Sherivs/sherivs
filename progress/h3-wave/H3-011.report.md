# H3-011 — §42 Mission Report (B-011 / J-010, Lockdown Path Engineer)

## Implemented

Emergency revocation / kill-switch semantics depth on
`frontend/src/lib/security/lockdown.ts` — strictly additive; every pre-existing
export, law and behavior preserved:

1. **Emergency kill-switch revocation — `revokeLockdown` (new).** The fast
   off-switch distinct from the independent lift: ANY authorized guardian —
   including the declarer — may revoke a false alarm or mis-scoped lockdown
   instantly (§18 enforcement must never wedge an incident closed). The
   locked-out agent can NEVER revoke (`self_revoke_denied`, §5). Non-empty
   reason mandatory; active-state required; every attempt audited
   (`LOCKDOWN_REVOKED` / `LOCKDOWN_REVOKE_DENIED`); pure (new frozen
   declaration, original untouched); terminal (no revoke/lift/renew revival).
   Revocation only STOPS a deny — it never grants anything, which is what
   makes the looser-than-lift authority safe by construction.
2. **Bounded renewal — `renewLockdown` (new).** The emergency window extends
   only by a guardian OTHER than the declarer (`renewal_independence_denied` —
   no indefinite self-extension), only by a targeted agent never
   (`self_renew_denied`), only strictly forward past the current expiry
   (`renewal_expiry_invalid`), only under a mandatory caller-supplied expiry
   ceiling (`renewal_expiry_exceeds_cap`, `renewal_cap_invalid`) and a
   mandatory positive-integer renewal cap (`renewal_cap_reached`), only with a
   reason — audited on both outcomes (`LOCKDOWN_RENEWED` /
   `LOCKDOWN_RENEW_DENIED`). Renewal carries a per-declaration ledger
   (`renewalCount`, `lastRenewedAt/By/Reason`).
3. **`"revoked"` lifecycle state (additive).** `LOCKDOWN_STATES` extended to
   `[active, expired, lifted, revoked]`; `lockdownState` returns `revoked`
   for revoked declarations at any instant (terminal record wins over window
   decay). Existing active/expired/lifted paths byte-identical.
4. **`activeApplicableLockdowns` (new pure helper).** The full deny-wins
   blast-radius view: every active declaration covering a request — including
   ones whose exemption would clear it (an exemption never bypasses another
   applicable lockdown).
5. **Zod v4 contract layer (new).** Strict schemas
   (`lockdownExemptionSchema`, `lockdownRequestSchema`,
   `lockdownDeclarationSchema`, 10-kind discriminated-union
   `lockdownAuditEventSchema`) + fail-closed parse helpers
   (`parseLockdownDeclaration`, `parseLockdownAuditEvent`,
   `parseLockdownRequest`) for lockdown artifacts crossing a trust boundary.
6. **`LockdownAuditEvent` union extended** with the four new event kinds; the
   `LockdownDeclaration` shape gained optional revocation/renewal fields,
   initialized by `declareLockdown`.

## Security Validation

- Fail-closed: non-guardian revoke/renew → `guardian_not_authorized`; empty
  reason → `revoke_reason_required` / `renewal_reason_required`; non-active →
  `lockdown_not_active`; locked-out agent blocked (`self_revoke_denied`,
  `self_renew_denied`); declarer cannot renew (`renewal_independence_denied`).
- No privilege escalation: revocation only stops a deny; renewal only extends
  a deny under a ceiling and cap; neither path grants any capability.
- Audit completeness (§18): all 10 event kinds emitted and parsed; denied
  attempts audited; test asserts the exact event sequence for the
  declare→deny→revoke→denied-re-revoke→denied-renew lifecycle.
- Tamper resistance: Zod strict objects refuse unknown keys (e.g. a smuggled
  `escalationHint` on an audit event), non-enumerated scopes, missing reasons,
  and negative renewal ledgers; `LOCKDOWN_ALLOW_ALL`-style unknown kinds are
  refused.
- Immutability: revoked/renewed declarations are frozen; originals never
  mutated in place; terminal states cannot be revived by any operation.

## Known Risks

- `revokeLockdown` intentionally permits declarer self-revocation (the
  emergency off-switch). This is a semantic widening relative to lift, mitigated
  by: revocation grants nothing, is reason-mandatory, fully audited, and
  terminal. If operators want symmetric independence on release, restrict the
  allowlist — the contract already enforces whatever allowlist it is given.
- `parseLockdownDeclaration` validates shape/bounds, not business rules
  (wildcard exemptions etc. remain the responsibility of `declareLockdown`);
  artifacts from other producers must still be re-validated by callers.
- New `LockdownDeclaration` fields are optional to preserve assignability of
  older serialized declarations; `lockdownState` treats absent `revokedAt` as
  not-revoked (backward compatible).
