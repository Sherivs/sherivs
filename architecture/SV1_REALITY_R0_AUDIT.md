## Executive finding

The repository already has a Scholar educational operating model, configuration discovery and governance, typed Scholar relationship validation, a universal kernel entity/relationship/event/observation substrate, and domain-owned school, academic, HR, finance, and operations records. The Scholar operating model is published as the `scholar.institution.operating_model` `cg_entity` type with blueprint version metadata; it is not a new `institution_reality_manifest` table. Reuse this work rather than create another organization, HR, role, workspace, graph, scheduling, website, or twin system.

However, the epic's single cross-domain Reality Core and dependency resolver are not established as one operational, shared contract consumed by both discovery and workforce. Existing representations remain split between the universal tenant/entity layer, Scholar's configuration and legacy `school_id`-scoped records, workforce/role assignments, and other domain-owned records. The code has partial temporal, lifecycle, evidence, and simulation primitives, but does not show one end-to-end model for the epic's Discovered / Approved / Operational states, its confirmed / inferred / unknown / conflicting / pending classifications, or effective-dated historical configuration across those domains.

This is an inventory and proposal, not authorization to close those gaps. The repository's Phase 04 ACTIVE-V1 classification applies to its existing education-runtime envelope; it does not unfreeze V3 Reality Intelligence or authorize R1+ work.

## Audit method and evidence limits

- “Existing” means a source artifact or contract was found in this checkout; it does not assert that a migration is deployed or a workflow is end-to-end operational.
- The kernel bitemporal migration explicitly says **AUTHORED, NOT APPLIED**. The kernel substrate's checked-in migration enables RLS, revokes `anon`/`authenticated`, and grants `service_role`; this is deny-by-default, not evidence that every consumer has a tenant-readable RLS policy.
- `education-reality-view` and its tests remain, but the Phase 04 acceptance record says the former `/admin/education-reality` surface was removed and the projection is **IMPLEMENTED_UNWIRED**.
- The cited `phase-04-education-reality-engine.md` is an architecture specification, not proof that each specified capability is implemented.
- Linked issue status was checked on 2026-11-01: #196, #207, and #135 are merged. #227 and #223 remain open with separate draft audit PRs #228 (scheduling S0) and #224 (twin T0). Their results are dependencies to reconcile, not work to duplicate.

## Proposed database and ownership changes

**R0 recommendation: no migration and no new canonical data table.** This is a proposal for a future, explicitly authorized design review only.

1. Treat the existing `scholar.institution.operating_model` entity as the candidate manifest anchor and define a typed, versioned contract over it. First test whether the current `cg_entity` attributes, validity/supersession fields, `cg_relationship`, `cg_observation`, and `cg_event` can carry the required semantics. Do not add a competing `institution_reality_manifest`, graph, identity, HR, or role store.
2. Keep canonical facts in their owning domains. The manifest may reference those records through same-tenant IDs/relationships; it should not become a shadow copy of grades, fees, staff, schedules, or facilities.
3. Use the neutral tenant/org key on any shared manifest or relationship. Existing `school_id` schemas remain behind their current domain adapters unless a separately approved migration establishes and verifies a mapping; R0 does not rewrite those tables.
4. Preserve distinct state dimensions in the typed manifest/assertion contract: discovery status, approval decision, operational status, and epistemic classification. Do not encode `inferred` or `unknown` as confirmed canonical state, and do not overload the generic `cg_entity.state`.
5. Before proposing database changes for effective dates, reconcile the existing kernel temporal columns and the authored bitemporal migration. Require explicit effective-time semantics, immutable transaction-time history, same-tenant references, and a documented supersession/correction path. Do not introduce a second version-history table by default.
6. Require tenant isolation at both layers for any authorized future write path: tenant-appropriate database RLS and server-side authentication, tenant resolution, authorization, schema validation, audit, and allowed-data response. A service-role adapter must resolve tenant and authority before any database operation; service-role access does not replace the required RLS boundary.
7. If R1 proves that required, queryable fields or constraints cannot safely live in the existing substrate, return with a narrowly scoped additive proposal keyed to the existing entity and tenant, including constraints, indexes, forced/appropriate RLS posture, rollback, and verification evidence. Do not pre-emptively create a domain-wide schema in R0.

## Dependency analysis and proposed sequencing

The dependency direction is a prerequisite graph, not an implementation plan authorization:

```text
server-resolved identity + neutral tenant/org boundary
  → existing Scholar operating-model baseline and version
  → typed assertion/provenance/confidence semantics
  → domain-owned entity/relationship contract + dependency validation
  → Engine A discovery ─┐
                        ├→ approved shared Reality Core
  → Engine B workforce ─┘
  → blueprint validation and non-mutating simulation
  → separately approved transactional/idempotent implementation
  → authorized domain integrations (scheduling, website, twins)
```

- R1 must reconcile to ACTIVE-V1 Phase 04 and the V3-frozen Reality Intelligence boundary before defining new shared capabilities.
- R2 must use the existing graph owner and define dependency types, same-tenant traversal, validation, cycle/contradiction behavior, effective-time evaluation, and impact semantics before any conversational AI layer.
- R3 may use existing configuration discovery as a starting point, but any natural-language extraction must remain a proposal with explicit provenance/confidence and human confirmation. AI is not a system of record.
- R4/R5 depend on R1/R2 and the existing blueprint/governance/simulation owners. Production writes require a separately authorized transactional design with idempotency, rollback/recovery, and audit; simulation remains isolated from production.
- R6 consumes #196 and the existing workforce/identity/workspace owners; it must not redefine roles, responsibilities, permissions, or workspace grants.
- R7 consumes the existing Phase 12 owner. #227/#228 are open; resolve any scope/classification conflict there before changing scheduling.
- R9 consumes website generator #135 and may publish presentation output only from approved canonical state.
- R10 depends on twin issue #223/#224 and its separate scope gate; no assistant context or cross-tenant retrieval is authorized here.

The master dependency doctrine in `DEPENDENCY.md` distinguishes ownership, runtime invocation, data ownership, authority, and trust. The implementation plan must preserve those dimensions rather than model every connection as one generic “depends on” edge.
