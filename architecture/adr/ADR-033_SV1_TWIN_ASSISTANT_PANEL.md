## Context

The workspace shell already has an assistant screen whose client reports that no service is connected. The twin's proposals (ADR-032) need a place where a person can read the brief for what happened while they were away and approve or dismiss items. The UI must not trust the browser for identity or tenant, must show how old the data is, and must not let a decision be made on data that may have changed.

## Decision

(1) A client port, `twin-brief-client.ts`, with the same shape as the assistant client: with no transport it reports `unavailable`, so the panel says so and shows nothing invented. Requests carry only an operation and a proposal id; identity, tenant and role are never sent, and the server is expected to resolve them. Responses are untrusted: parsed field by field, unknown fields dropped, cards without a label, source or valid kind dropped and counted, a label that does not match the kind rejected, predictions forced to non-actionable. (2) A pure view model, `twin-brief-model.ts`, holds the rules. The cache lives in memory only and is keyed to the exact identity, organization and role; any change drops it. A cached brief is always shown with its age. Approve needs a live brief no older than 15 minutes and a source no older than 24 hours; dismiss and acknowledge need a connection because each is a server call; nothing is queued offline, so no decision is replayed later against changed data. Source freshness is computed in the browser from the as-of time rather than trusted. (3) A thin panel, mounted in the assistant screen, with a confirmation step before approval, a polite live region, named controls with 44 px targets, focus moved into the confirmation and back on cancel, text rendered as text, and a reduced-motion rule. (4) A DEV-only demo fixture added to the existing local workspace preview, with synthetic data and controls for empty, unavailable, error, offline and elapsed-time states.

## Consequences

Until a server operation exists and a transport is wired, the panel shows 'not available yet' in every environment; no brief reaches a user. The server operation, its authorization and its use of the proposal rules (ADR-032) are a later mission and need their own review. The 15 minute and 24 hour thresholds are proposals for owner review. The context key used to scope the in-memory cache is built from ids the shell already holds and is never sent anywhere. Because the cache is in memory, a page reload loses the offline brief; that is deliberate, since persisting a brief offline would need privacy review and a migration in the reserved block 20261103162000–162999, which this mission does not use.

## Verification

`tests/unit/sv1-twin-brief.test.tsx` (34 tests) covers the client (no identity sent, unavailable and error handling, untrusted parsing, label and kind rules), every view model state (live, stale, offline with and without cache, unavailable, loading, error, empty, other-context cache), every enabled and disabled action with its reason, server-rendered markup (landmark, live region, accessible names, describedby targets, confirmation step, escaped markup) and source guards (no network, storage, database or HTML injection; no identity read in the panel). 20 deliberate mutations were each caught; two guards that were redundant with parsing needed extra tests and one mutation produced an equivalent program. A browser run of the local fixture at 1440 and 390 px covered live, confirm, stale, offline-cached, unavailable and empty states: no horizontal overflow, no unnamed buttons, no target under 44 px, no text under 4.5:1 contrast, focus moves into the confirmation and back, and a reduced-motion rule is present. Evidence is under `docs/evidence/twin-05/`. Related shell suites pass (403 tests across 13 files). No CI evidence exists because the organisation billing hold blocks Actions.
