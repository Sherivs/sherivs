## Context

ADR-005 ruled the erasure mechanism for personal data inside immutable records — redaction-with-tombstone: nothing is ever mutated or deleted; erasure appends an erasure audit event and tombstones subject-identifying personal values through a redaction projection layer. ADR-005 was explicit about the cost of that ruling: redaction is *policy-level* erasure, not *bit-level* — "any reader that bypasses the redaction layer (raw database access, old backups, pre-existing replicas) can still see personal values" — and therefore demanded "a documented backup-expiry discipline." ADR-008 carried that demand into contract invariants B-1..B-4 (manifest completeness; lifetime bound `expiresAt` ≤ the earliest retention deadline among contained families; backup reads through the redaction layer; restore re-applies redaction state) and stated the residual exposure honestly: a subject erased **after** a backup was taken remains readable inside that artifact until its `expiresAt`.

What no artifact yet rules — and what this ADR rules — is the underlying structural conflict stated as a decision:

1. **Backups cannot honor per-record erasure.** A backup is, by the nature of backup media, an offline snapshot: it is written once, stored self-contained (often off the canonical substrate, in provider object storage or off-platform), and intentionally immutable *as a copy* — its evidentiary value for disaster recovery depends on checksums and manifest integrity (RESTORE_RECOVERY_RUNBOOK_MR101 obligations). There is no mechanism by which a later per-record tombstone event in the canonical substrate reaches into an existing backup artifact and redacts one subject's values. Any "rewrite the backup" mechanism would destroy the copy's integrity evidence and would itself be the mutation the tombstone law forbids.
2. **The erasure duty (Constitution §19) does not pause for backup cycles.** Personal data in a backup is still personal data; a backup that outlives the lawful retention of the data it contains *is* an erasure violation — the values remain readable in the copy even though the canonical record is fully tombstoned.
3. **The retention schedule is live and heterogeneous.** RETENTION_POLICY_SCHEDULE.json (V1CAP-066 binding, validated by `scripts/verify-retention-schedule.mjs`) keys 28 policies by (recordFamily, dataClassification, tenantClass). Windows differ by more than an order of magnitude: `ai-snapshot` expires at 180 days (`RP-AISNAP-*`, the shortest window — child and student prompt/response content), `audit` at 2555/1825 days (`RP-AUDIT-EDU/ORG/PLT`), and several families are event-triggered (`memory`: purpose-expiry with a 365-day backstop; `biometric-reference`: consent-withdrawal-or-enrollment-end with immediate erasure on consent withdrawal regardless of the backstop). A single backup typically spans multiple families, so a single flat backup TTL cannot satisfy the schedule — the bound must be computed per backup from the *most short-lived* family it contains.

The reconciliation must therefore be temporal, not mechanical: erasure reaches backups through **time** (expiry on the retention schedule) plus **restore-time re-application** of redaction state, never through mutating the copy. ADR-008 stated this as "what the substrate never forgets, redundant copies must not outlive"; this ADR makes that sentence a ruled discipline with explicit consequences, an explicit residual risk, and a named owner.

## Options

### Option 1 — Erasure-by-mutation: rewrite or patch backup artifacts per erasure event (rejected)

When an erasure event lands in the canonical substrate, locate the subject's values inside every existing backup artifact and rewrite, re-encrypt, or re-pack the backup to remove them.

- **Consequences:** would in principle shrink the residual window toward zero without waiting for expiry. Rejected on three independent grounds. First, it is the mutation class the tombstone law forbids, relocated into the backup path — ADR-005's ruling ("immutable records are tombstoned, not deleted") and §28's audit-integrity invariant apply to anything that functions as record evidence, and a backup whose bytes can be silently rewritten per erasure event is no longer trustworthy recovery evidence (its checksums and manifest become restatable). Second, it introduces a standing **cross-record write path into offline media** — a new attack and error surface (a bug in the rewriter corrupts the only recovery copy precisely when it is most needed) with no corresponding authorization model (backup media is typically outside the RLS perimeter; §17's deny-by-default cannot contain it). Third, it is mechanically unenforceable for compressed/encrypted/append-only backup formats and for artifacts held by a provider.

### Option 2 — Make backups erasure-capable by construction: crypto-shred-scoped backups (rejected as the V1 general mechanism, retained as future hardening)

Encrypt every backup per data class or per subject with gateway-held keys; erasure destroys the key, and the backup ciphertext becomes permanently unreadable per record class — bit-level erasure without touching bytes.

- **Consequences:** resolves the residual window in the strongest way ADR-005 considered (its Option 1) and would also cover event-triggered immediacy (e.g. biometric consent withdrawal). Rejected for V1 for the same grounds ADR-005 recorded: the substrate evidences no key-management capability anywhere (no KMS family); key loss becomes an availability failure mode inside the recovery path; and restore now depends on key availability as well as artifact integrity — J-042 must restore keys and ciphertexts consistently or the backup resurrects nothing. ADR-005 deferred crypto-shredding to a follow-up ADR unless the operator designates a shred class (the schedule flags `biometric-reference` as `cryptoShredCandidate`, pending COND-009). If that designation ever lands, this ADR's Option 3 discipline remains the fallback layer for all non-shred classes, so ruling Option 2 down now does not foreclose it.

### Option 3 — Temporal expiry discipline: backups expire on the retention schedule; restore re-applies redaction state (ruled)

Backups are ruled **redundant copies with a bounded lifetime, never canonical records and never erasure participants**. Per-record erasure never reaches into a backup artifact by mutation; instead:

1. **Manifest-bound lifetime (B-1/B-2 binding).** Every backup artifact containing any personal-data-bearing record family carries a manifest recording `takenAt`, the per-family retention policy IDs (resolvable in RETENTION_POLICY_SCHEDULE.json), the redaction projection state at backup time, and `expiresAt` ≤ the earliest possible retention deadline among the families it contains, computed conservatively from `takenAt` and the youngest record ages. A backup MUST never outlive the lawful retention of the most short-lived personal data it holds (e.g. a backup containing `ai-snapshot` content expires within that family's 180-day window). Expired artifacts are destroyed **as redundant copies** — destruction of an expired copy is not record destruction and touches no canonical record.
2. **Flat TTLs are forbidden.** A single platform-wide backup retention number cannot satisfy a schedule whose windows range from 180 days (`RP-AISNAP-*`) to 2555 days (`RP-AUDIT-EDU/ORG`); the `expiresAt` computation is per-manifest, from phase 14's schedule, owned by phase 21.
3. **Backups read through the redaction layer (B-3).** A backup taken after a record's erasure contains the tombstoned rendering — backup reads and verification go through the redaction projection, never raw.
4. **Restore re-applies redaction state (B-4, the J-042 verifiable invariant).** Any restore replays the tombstone/redaction projection state recorded in the manifest, and the ADR-005 erasure invariant must hold over the restored dataset (*for every tombstoned record: the record exists, is non-readable as personal data through the redaction layer, and its erasure event is present and well-formed*). A restore that resurrects pre-erasure personal values is a FINDING (exit 1) — the same exit-0/1/2 semantics `scripts/restore-recovery-drill.mjs` and the H3 recovery-drill exemplar already produce.
5. **Observability (§29).** Backup creation, expiry destruction, and restore-with-re-redaction are logged and auditable events with provenance (who, when, under which policy IDs); expiry destruction is never silent.

- **Consequences (honest costs):** the residual window of Option 1 does not exist here by construction — but the reverse cost is real and is ruled below as the explicit residual risk. Also: heterogeneous schedules make manifests mandatory bookkeeping (a backup without a complete manifest is non-compliant by construction, not by after-the-fact review); expiry destruction must be automated to be trustworthy (manual TTL hygiene is the historically proven failure mode of this discipline); and restores become verification-gated, which is operational cost paid to make "restore never resurrects erased data" checkable rather than assumed.

## Recommendation (decision)

**Option 3 — the temporal expiry discipline — is the V1 ruling.** Option 1 violates the tombstone law by relocating mutation into the backup path and destroys the evidentiary property that justifies backups; Option 2 depends on key-management infrastructure the corpus does not evidence and ADR-005 explicitly deferred. Option 3 matches the substrate as it exists: per-record erasure stays a canonical-substrate act (tombstone + redaction layer, ADR-005 unchanged), while erasure reaches redundant copies through a bounded lifetime computed from the live retention schedule and through restore-time re-redaction — the same "policy-level erasure bounded by X" pattern ADR-005 used for the redaction layer (bounded there by access control, here by time).

### Explicit residual risk (stated, bounded, owned — not hidden)

- **The residual risk:** personal data erased **after** a backup was taken remains readable inside that existing artifact until its `expiresAt`. Erasure reaches such backups on the backup's expiry schedule, not instantaneously. For duration-keyed families this window is bounded by B-2 (≤ the earliest retention deadline among contained families; worst practical case for a backup containing only `ai-snapshot`: up to 180 days from the youngest record's `created_at`).
- **The sharpest instance:** event-triggered families with immediate erasure duties — above all `biometric-reference` (RP-BIOMET-EDU: erasure immediate on consent withdrawal regardless of the backstop). A biometric reference enrolled and backed up days before a consent withdrawal persists in that artifact until `expiresAt` even though the canonical record was erased the same hour. Special-category data surviving erasure in a copy is the least acceptable form of this residual risk; the sanctioned narrowing path is the operator designating biometric-reference a crypto-shred class (COND-009 + operator ruling, per the schedule's `cryptoShredCandidates` note), at which point Option 2 applies to that class and this discipline remains the layer for everything else.
- **The accepted rationale:** the window is bounded by the operator's own retention ruling (the schedule), the copies are access-controlled and read only through the redaction layer (B-3), the bound is disclosed in the V1CAP-066 contract, and eliminating it entirely requires either the mutation forbidden by §28 or infrastructure (KMS/shred-class designation) not present in V1. Erasure-with-a-time-bound is the only formulation simultaneously lawful-in-mechanism and implementable-now; it is the same accepted trade ADR-005 made for the redaction layer.
- **Owner of the residual risk:** **phase 21 (infrastructure) as the J-042 capability owner (V1CAP-074)** — it owns backup manifests, the `expiresAt` computation from phase 14's schedule numbers, expiry-destruction automation, and the restore re-redaction gate; it reports the residual-window posture to the operator alongside the V1CAP-066 contract. Phase 09 (audit immutability boundary) owns the rule that backup destruction never touches canonical records; the verify pipeline (V1CAP-066's verification owner per ADR-005) owns invariant checks E-1..E-4 and B-4. Mitigations that narrow but do not close the window (shred-class designation, shorter provisional `ai-snapshot` durations) are operator rulings, not phase-21 acts.

## Consequences (summary)

- **Positive:** the erasure duty and the backup capability are reconciled without mutating any copy or any canonical record; `expiresAt` becomes a machine-checkable manifest field derivable from the already-live retention schedule; restore gains a checkable no-resurrection invariant (B-4) with existing drill semantics; expired-copy destruction is legalized as non-destruction, unblocking retention hygiene for backup storage itself.
- **Negative / obligations:** backup manifests are now compliance-critical (incomplete manifest = non-compliant artifact); expiry destruction must be automated and observed, not manual; every restore path must implement re-redaction replay or it is a FINDING by construction; the residual window above must be disclosed in the V1CAP-066 contract; biometric-in-backup persistence remains until a shred-class ruling.
- **For the H3 wave specifically:** A-003's backup-manifest contract is the type surface this discipline binds (`takenAt`, per-family policy IDs, projection state, `expiresAt`); A-001's rehearsal validates manifest shapes against it; A-007's failure tests own the expired-backup-set and corrupt-manifest failure paths this ADR makes non-compliant.

## Golden Questions

- **WHO?** Phase 21 (J-042 owner, V1CAP-074) owns backup manifests, expiry computation, destruction automation, and the restore gate — and owns the residual risk above; phase 14 supplies the schedule numbers the bound is computed from; phase 09 owns "copy destruction is not record destruction"; the verify pipeline owns E-1..E-4/B-4 checks; the operator rules this ADR and any shred-class designation.
- **WHAT?** Backups are bounded-lifetime redundant copies: manifest-bound `expiresAt` ≤ the earliest retention deadline among contained personal-data families; never mutated per erasure event; read through the redaction layer; restores re-apply redaction state; expired copies are destroyed as copies.
- **WHERE?** The discipline lives in this ADR; its numbers in RETENTION_POLICY_SCHEDULE.json (phase 14); its mechanics in phase-21 backup tooling and manifests; its checks in the verify pipeline and the restore/recovery drill discipline; its typed consumer in the H3 wave's `frontend/src/lib/reliability/backup-manifest.ts` contract (mission A-003).
- **WHY?** ADR-005 demanded a backup-expiry discipline and left it open (UNKNOWN 4); ADR-008 defined the invariants but recorded that mechanical enforcement has no owner-authored tooling yet and left the residual window unruled. A platform holding child and staff personal data cannot let erasure stop at the canonical substrate while the same values persist in copies indefinitely — and cannot mutate backups either without destroying the audit and recovery evidence §28 exists to protect.
- **UNDER WHICH POLICY?** ADR-005 (tombstone law, implementation-path step 4, UNKNOWN 4); ADR-008 (B-1..B-4, residual-exposure statement — unchanged and here bound); RETENTION_POLICY_SCHEDULE (V1CAP-066 binding schedule, per-tenant-class policy IDs, provisional-duration caveat); AGENTS §12 (provenance on manifests, destruction, and restores), §17 (RLS deny-by-default; redaction layer is the only read path), §19 (expired purpose and authorized-information bounds apply to copies), §21 (AI output trust; erased AI-snapshot values must not resurrect), §28 (immutable canonical records; backups never become a mutation path), §29 (observable destruction and restore), §31 (tests must prove restore never resurrects erased values and expired artifacts fail verification); Constitution §19 (erasure duty per J-039), §9 (a restored dataset is canonical truth only after the erasure invariant holds — re-redaction is validation, not inference); RESTORE_RECOVERY_RUNBOOK_MR101 (executed manifest obligations, VERDICT=PASS).

## UNKNOWNs

- **Operator ratification:** this ADR is PROPOSED; the discipline binds when the operator rules it (it is drafted to require no schema or dependency change, so ratification is the only gate).
- **Event-triggered deadlines are not exactly computable at manifest time:** a `purpose-expiry` or `consent-withdrawal` trigger can fire at any moment after backup; B-2's `expiresAt` must therefore be computed from the *backstop* (`maxRetentionDays`) conservatively — which means the effective residual window for event-triggered families is bounded by the backstop, not by the trigger. A tighter per-record bound is impossible without Option 1's mutation or Option 2's keys.
- **Expiry-destruction automation is a phase-21 deliverable, not yet tooling:** no storage-level TTL machinery exists in the repository today; until it lands, expiry discipline is procedural (drill + manifest review), and the residual window's enforcement is audit-based rather than mechanical. The H3 recovery-drill runner (A-001) and failure tests (A-007) establish the verification shape, not the destruction mechanism.
- **Restore-time re-redaction (B-4) in CI without live credentials** (J-041 issue) remains open, carried unchanged from ADR-005/ADR-008; the drill requires serialized canonical access.
- **Replicas and change streams** (AGENTS §35): whether they inherit this discipline or need their own erasure-propagation rule remains assumed-yes-by-policy and mechanically unverified — carried forward unchanged; this ADR neither resolves nor narrows it.
- **The V1CAP-066 contract text disclosing the residual window** is not yet authored (the schedule's provisional durations are also still pending operator/legal ruling); disclosure is an obligation of this ruling, not yet an artifact.
