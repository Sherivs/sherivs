## Context

A personal twin may suggest, but it must never change a canonical record. The Scholar AI safety boundary already forbids AI from mutating records, policy, permissions or grades; the twin needs a proposal model that makes that boundary concrete: every suggestion shows what it is and where it came from, a person approves or dismisses it, and only an approved command runs, through the operation contracts that already require authorization.

## Decision

Add one pure module, `proposals.ts`. (1) Four proposal kinds, each with a fixed visible label, and a mandatory source (kind, opaque reference, as-of time, one-line description). (2) Creation checks: a bounded summary and time to live; an operation, when named, must be declared in the operation contracts, be a command and require authorization; the `propose` action must pass `decideAiAction` under the lens role; a permission the operation needs must be named. (3) Predictions carry a confidence between 0 and 1, cannot name an operation and can only be acknowledged or dismissed. (4) Only the owning user in the same tenant can approve, dismiss or acknowledge; approval requires that the named permission is held now, as supplied by the server. (5) Approval is consent only. `prepareExecution` re-checks the contract and the held permission, then returns a frozen request description with an idempotency key and moves the proposal to handed-off once; it calls nothing. (6) `recordExecutionOutcome` records what the authorized operation reported. (7) Every step appends an audit record with the correlation id. (8) The away brief lists only my open, unexpired proposals, newest source first, bounded, with a stale mark when the source is old. (9) Playbooks instantiate only the steps the person's permissions already allow, so a playbook can only narrow. (10) The growth ledger is append-only, owned by one person, records only decided proposals or the person's own notes, and has a gap-free sequence check. A guard test scans every module in the twin directory and fails on a database client, server function, network call, storage access, timer or any import outside an explicit allowlist.

## Consequences

No twin code path can write a canonical record: the module has no write capability to misuse, and the guard test keeps it that way for every twin module added later. Proposal and ledger state is held by the caller; persisting it would need a migration in the reserved block 20261103161000–161999, which this mission does not use, and any such table would need forced RLS and owner-only access. No proposals are generated yet: a source of recommendations (rules, the AI gateway) is a later, separate decision. The default time to live ceiling (seven days), summary length (280) and note length (500) are proposals for owner review. The execution request is a description only; the host that sends it and the server operation that re-authorizes it are outside this mission.

## Verification

`tests/unit/sv1-twin-proposals.test.ts` (36 tests) covers labels and sources, creation rejections, prediction rules, owner and tenant checks, permission checks at approval and again at handoff, one-time handoff with idempotency key, outcome recording, audit order and correlation, cards and stale marks, the away brief, playbooks, the growth ledger, a 3000-step seeded random sequence, and the source guard. `tests/unit/sv1-twin-proposals-safety.test.ts` (2 tests) replaces the AI safety boundary with a denying stub to prove the module honours it. 18 deliberate mutations were each caught by at least one test (one survived at first because the safety check is redundant with earlier checks, so the stubbed-boundary test was added). `tests/unit/scholar-ai-contracts.test.ts` still passes. No CI evidence exists because the organisation billing hold blocks Actions.
