# Sherivs Information Architecture

Status: Target IA; capability availability remains authoritative  
Version target: ACTIVE-V1

## Organizing model

Users should answer four questions at any point: **where am I, what am I seeing, why can I see it,
and what may I do next?** Global hierarchy:

1. Sherivs platform context
2. Organization
3. Workspace
4. Domain/runtime
5. Object or task
6. Evidence and activity

## Navigation hierarchy

- **Global:** organization/workspace context, search, command, Jarvis, notifications, help, profile.
- **Workspace:** capability-derived primary destinations.
- **Section:** local tabs or subnavigation for one bounded domain.
- **Contextual:** actions and supporting panels for the selected object.
- **History:** activity, audit, evidence, verification.

Breadcrumbs represent location, not interaction history. Back controls represent history. Tabs
switch peer views without changing object identity. Filters refine a collection and persist in URL
state when shareable.

## Public IA

The Sherivs public narrative follows:

Brand → category need → organizational model → contextual intelligence → governed workers →
missions/evidence → adaptive experience → Scholar runtime → governance → architecture → future
direction → verified CTA.

This is editorial progression, not a card catalog. Security, legal, accessibility, contact, and
status remain directly discoverable from every public page.

## Organization public IA

Identity, about, services/programs, locations, leadership/people, departments, events,
announcements/news, resources/documents, public forms, contact, careers, policies, accessibility,
and footer. Each section is capability- and publication-policy-driven. Admissions, curriculum,
student life, parent portals, and similar education concepts are Scholar contributions.

## Organization workspace IA

Potential destinations are Overview, People, Teams, Work, Missions, Knowledge, Communications,
Calendar, Tasks, Files, Data, Reports, Automation, AI Workforce, Integrations, Analytics,
Governance, and Settings. None is universally visible. Runtime, capability, policy, relationship,
and current context determine composition.

“Reality,” autonomous workforce, universal memory, and other labels that imply frozen V3/future
scope must not be enabled beyond proven ACTIVE-V1 organizational records and bounded workers.

## Sherivs internal IA

Executive, Jarvis, Missions, Customers, Organizations, Product, Engineering, Architecture,
Infrastructure, Security, Operations, Support, Finance, Research, Analytics, Releases, Incidents,
Governance, and Documentation. Access requires a Sherivs platform-workforce identity and explicit
department/resource permissions. Customer users never discover internal destinations.

The UI indicates current scope in every settings title and destructive confirmation.

## Search and command

Universal search returns permitted people, organizations, workspaces, missions, documents, files,
knowledge, events, tasks, communications, workers, settings, help, and public content. Results
carry type, context, freshness, and reason for relevance. Search indexes are derived and filtered
by server authorization.

Command discovers authorized actions. Each command declares required capability, input schema,
consequence, approval requirement, idempotency behavior, and destination. Execution re-authorizes.

## AI information anatomy

Jarvis and contextual intelligence responses use stable sections:

1. Observation — sourced state.
2. Inference — derived interpretation with uncertainty.
3. Recommendation — non-authoritative proposal.
4. Action — available or proposed governed command.
5. Evidence — sources and provenance.
6. Verification — independent outcome state.

## Mobile IA

Primary bottom navigation contains the current workspace’s highest-frequency destinations, never
the full desktop tree. A context header handles organization/workspace switching. Search/command
is globally reachable. Secondary destinations live in a sheet; object actions remain near the
object; tables transform to priority lists or comparison sheets.

## Naming

Use organization-neutral language in platform surfaces: organization, member, workspace,
capability, resource, policy. Runtime surfaces may use domain language such as school, teacher,
student, parent, class, or admissions. “CoreGrid” remains only in technical/historical contexts
during compatibility migration.
