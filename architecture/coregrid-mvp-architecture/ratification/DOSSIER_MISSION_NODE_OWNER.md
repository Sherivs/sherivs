## 3. Candidate A — phase 07 owns the Mission node

**The case for A:**

1. Co-location with the rest of the loop's tail: STREAM F assigns phase 07 ownership of the **Delegation and Worker Execution** loop nodes ("Owns Delegation and Worker Execution loop nodes… The D6 duplication cluster is CLOSED with owner 07", `STREAM_F_PHASE_EXTRACTION.json#phases[07].v1Justification`). The Mission -> Delegation -> Worker spine is contiguous; one phase owning all three would minimize ownership seams (J-025's delegation-contract owner is already "phase 07 + ratified Mission owner", `STREAM_J_GAP_DISCOVERY.json#…gaps[J-025].proposedOwner`).
2. Precedent of closing a cluster on the implementer: the registry closed D6 (agent cluster) on owner 07 even though other phases touch it (`architecture/registry.json#duplications[D6]`, cited in STREAM F phase 07 evidence).
3. Phase 07 is V1-required and already carries the worker LAUNCH_BLOCKER gap (`COREGRID_V1_CAPABILITY_CATALOG.json#capabilities[area=worker]` — "LAUNCH_BLOCKER"), so it is an active, V1-owned phase — unlike the substrate, which has no phase number.

**The case against A (evidence AGAINST the candidate):**

1. **Executor-owns-governance concentration.** Phase 07 is the *worker/agent substrate*. Making the agent system also the canonical owner of mission orchestration places the governed-work spine inside the component being governed — the exact inversion AGENTS.md §7/§21 forbid ("AI output is untrusted by default; critical actions require AI Proposal -> Validation -> Policy Check -> Approval -> Execution -> Audit"). The mission loop is the approval-and-audit spine over agents; it must not be owned by them. This is an architectural-integrity objection, not a preference.
2. **It contradicts a recorded authority decision.** FM001-D1 records: "Mission orchestration is control-plane mechanism 06 … It is not a workflow engine, execution engine, verification engine, or architecture authority" with owner `CONTROL-PLANE-06-MISSION-ORCHESTRATION.md` (`COREGRID_FOUNDATION_MISSION_001_AUTHORITY_DECISION.json#decisions[FM001-D1]`). Ruling for 07 would overturn a recorded human-delegated decision (decidedAt 2026-09-29, authorizedBy "human-delegated-session-2026-09-29") without new evidence.
3. **No implementation to inherit.** The mission substrate that is live-verified (admission, idempotent replay, evidence, verification, rollback — STREAM H reusable[0]) is not phase 07 code. Ruling for 07 would orphan the only live-verified governed tail from its owner, forcing either a rebuild (forbidden by M-R-50: "Built on the live-verified foundation-mission loop …, never rebuilt", `COREGRID_V1_MISSION_GRAPH.json#missions[MISSION-R-50].objective`) or an awkward ownership-without-code arrangement.
4. **07 is already overloaded and gap-bearing.** 07 carries the worker substrate LAUNCH_BLOCKER (J-027) and would take the delegation contracts (J-025). Adding the Mission node increases the blast radius of the single most gap-dense V1 phase (STREAM J Workforce Fabric).

## 4. Candidate B — the control-plane/foundation-mission substrate owns the Mission node (presumed recommendation, tested)

**The case for B:**

1. **It is the only live-verified governed tail in the repo.** STREAM H reusable[0]: the foundation mission loop is "the ONLY end-to-end live-verified governed tail in the repo (admission -> idempotent replay -> evidence -> verification -> rollback), 5/5 live tests on the dev project" (`STREAM_H_IMPLEMENTATION_MAP.json#reusableVerifiedFoundations[0]`). Ownership law says a canonical owner exists; it does not say the owner must be a numbered phase. Ratifying the substrate ratifies ownership over code that demonstrably works.
2. **Authority for it is already recorded by a human-delegated decision.** FM001 assigns mission lifecycle to mechanism 06, evidence to 04, execution records to 08, verification to 09, conformance to 10 (`COREGRID_FOUNDATION_MISSION_001_AUTHORITY_DECISION.json#decisions`), and the substrate's own header cites that decision (`foundation-mission.ts` lines 4–8). The ratification would *confirm and generalize* an existing recorded ruling rather than create one.
3. **The scope lock already names it as proposed owner** (`COREGRID_V1_V2_SCOPE_LOCK.json#conditions[COND-001]`, `#blockingGaps[J-024]`; also `COREGRID_V1_RECONSTRUCTED_ARCHITECTURE.json#resolutions["Mission node ownerlessness (CG-GAP-003) > V1CAP-046"]`). Downstream artifacts (M-R-50, V1CAP-047, hardening L-H-004) were authored against this proposal; ratifying B changes the least.
4. **Separation of powers holds.** Under B, the agent system (07) remains a *consumer* of missions and the owner of the delegation/worker nodes — the substrate governs, 07 executes. This matches AGENTS.md §16's layered authorization and §21's approval spine.
5. **The catalog already leans this way**: area=mission owner is recorded as "phase-06-mission-mechanism" — i.e. the mechanism the substrate implements — with the only missing item being this ratification (`COREGRID_V1_CAPABILITY_CATALOG.json#capabilities[area=mission]`).

**The case against B (evidence AGAINST the presumed recommendation — recorded honestly):**

1. **The substrate's own authority boundary currently forbids persistence and live runtime.** `foundation-mission.ts` header: "The durable schema is authored separately and is not applied by this module. A live runtime remains unauthorized." FM001-D4: "This decision authorizes an in-memory contract only. No migration or durable store is approved" and FM001 `implementationBoundary.denied` includes "database migration" and "live runtime claim" (`COREGRID_FOUNDATION_MISSION_001_AUTHORITY_DECISION.json#implementationBoundary`). STREAM H flags the resulting tension explicitly: the morning report claims "live-verified on the dev project (5/5 live tests)" while every migration header declares "AUTHORED, NOT APPLIED. Do not treat this file as a live database"; live verification happened on a disposable Supabase dev project, and "the canonical/production database state has none of the cg_* tables" (`STREAM_H_IMPLEMENTATION_MAP.json#cautions[LIVE-VERIFIED vs NOT APPLIED]`). An operator could reasonably rule that the substrate is *not yet* owner-material until this authorization tension is resolved (durable schema applied, live-verification posture reconciled).
2. **The candidate list disagrees with itself.** J-024 and MISSION-R-01 T1 name the second candidate as "a new mission-artifact under phase 01 control-plane layer" (`STREAM_J_GAP_DISCOVERY.json#gaps[J-024]`; `COREGRID_V1_MISSION_GRAPH.json#missions[MISSION-R-01].tasks[T1]`) — i.e. create a new artifact under phase 01 — while the scope lock and reconstructed architecture name the *existing* substrate (`COREGRID_V1_V2_SCOPE_LOCK.json#conditions[COND-001]`). These are not the same ruling. Candidate B′ (new artifact under 01) would put the Mission node under the verify-pipeline phase; the substrate's recorded owner is mechanism 06, not phase 01, and phase 01's role in the mission fabric is verify-pipeline integration only (`STREAM_J_GAP_DISCOVERY.json#gaps[J-026].proposedOwner`).
3. **Placement concern: control-plane code lives under `frontend/src/lib/control-plane/`.** The substrate is TypeScript under the frontend tree (`frontend/src/lib/control-plane/foundation-mission.ts`, `foundation-loop.ts`), not a backend/infrastructure service. For a platform whose mission spine must serve every tenant and runtime, an operator may object that the canonical owner's implementation home is a UI-adjacent namespace. (Related governance question COND-013 — "domain server-function relocation timing + control-plane namespace" (`COREGRID_V1_MISSION_GRAPH.json#missions[MISSION-R-03].objective`) — is separately gated; its outcome could move this code.)
4. **The ownership map is stale relative to FM001.** The map (evidenceDate 2026-09-27) records `mission` as MISSING with `canonicalOwner: null`, but FM001 was decided 2026-09-29 (`COREGRID_ARCHITECTURE_OWNERSHIP_MAP.json#evidenceDate`; `COREGRID_FOUNDATION_MISSION_001_AUTHORITY_DECISION.json#decidedAt`). The map has not been updated; its null is evidence of a bookkeeping gap, and the dossier treats it as the *problem statement*, not as current truth. Conversely, if the operator considers FM001 itself to have already resolved mechanism-level ownership, the remaining open question is only whether mechanism-level ownership satisfies the phase-level ownership law.

**Testing the presumption:** the presumption survives. Every argument against B is either (1) a known tension already recorded in the evidence base that ratification would *surface and force to closure* (durable-schema application, live-vs-deployed posture), (2) a wording divergence between candidate lists that this dossier explicitly resolves in §5, or (3) a relocation timing question already gated separately (COND-013). No evidence was found that phase 07, phase 01, or any other phase has a stronger ownership claim than the recorded FM001 mechanism assignments plus the live-verified implementation. The recommendation below is therefore B, with B′ explicitly rejected.

## 5. Recommendation

**RECOMMEND: Candidate B — ratify the existing live-verified control-plane/foundation-mission substrate as the canonical Mission node owner (V1CAP-046).**

Rationale, in order of weight:

1. **Ownership law is satisfied by recorded authority + implementation, not by phase number.** FM001 (human-delegated, 2026-09-29) already assigned the mission lifecycle to control-plane mechanism 06 with MISSIONS.md as conceptual authority, and explicitly assigned the surrounding mechanisms (04/08/09/10) (`COREGRID_FOUNDATION_MISSION_001_AUTHORITY_DECISION.json#decisions[FM001-D1..D2]`). The substrate implements exactly that assignment and is the only live-verified governed tail (STREAM H reusable[0]).
2. **It preserves the separation between governance and the governed.** Phase 07 keeps Delegation/Worker Execution (its recorded loop nodes per STREAM F phase 07 v1Justification); the substrate owns Mission. The spine remains: substrate (06) coordinates -> 07 executes -> 09 verifies, matching FM001-D1's "is not a workflow engine, execution engine, verification engine, or architecture authority".
3. **It changes the least downstream.** COND-001's proposed owner, the scope-lock blockingGaps entry for J-024, V1CAP-046's owner field, L-H-004, and M-R-50's "never rebuilt" clause all already name or depend on this substrate (`COREGRID_V1_V2_SCOPE_LOCK.json`; `COREGRID_V1_RECONSTRUCTED_ARCHITECTURE.json#V1CAP-046`; `COREGRID_V1_MISSION_GRAPH.json#missions[MISSION-R-50].objective`).
4. **Candidate B′ (new artifact under phase 01) is rejected** because it would create a second mission-ownership decision surface where FM001 already recorded one, and it misplaces ownership with the verify pipeline (phase 01's recorded role is verification integration, not mission coordination — `STREAM_J_GAP_DISCOVERY.json#gaps[J-026].proposedOwner`).
5. **Candidate A is rejected** for the reasons in §3, principally the executor-owns-governance inversion and the contradiction with FM001-D1.

**Ruling formulation suggested for the operator:**

> The canonical owner of the Mission loop node (cg_mission_intent / cg_execution_record, V1CAP-046) is the control-plane mission substrate: mission-orchestration coordination owned by control-plane mechanism 06 per COREGRID_FOUNDATION_MISSION_001_AUTHORITY_DECISION.json (FM001-D1/D2), implemented by frontend/src/lib/control-plane/foundation-mission.ts + foundation-loop.ts + foundation-loop.functions.ts and the durable schema in migration 20260929000000_coregrid_foundation_mission_001.sql. Phase 07 remains owner of Delegation and Worker Execution nodes and a consumer of missions. Phase 01 remains verify-pipeline integrator (J-026 role). Ratification is conditional on closing the authorization tension recorded by FM001's implementation boundary (in-memory-only / no-migration / no-live-runtime) against the now-authored migration and live-verified battery — the durable-schema application posture must be ratified or re-scoped before V1CAP-046 contract work starts.

## 8. Contest points (for the operator to press)

1. **Does a non-phase substrate satisfy the ownership law?** The law says "one canonical owner" (`COREGRID_ARCHITECTURE_OWNERSHIP_MAP.json#ownershipLaw`) but the registry's phase-centric records (D-clusters, phase owners) assume owners are phases. If the operator requires a phase owner, Candidate A (07) is the only phase candidate — but see the objections in §3; an operator preferring a phase could alternatively direct that the substrate be *registered* as a phase or formally attached to mechanism 06's registry record (UNKNOWN: whether the registry supports non-phase owners — see §9).
2. **Is FM001 sufficient authority, or does ratification need to re-affirm it?** FM001 was scoped to "COREGRID-FOUNDATION-MISSION-001" (a single mission instance, `COREGRID_FOUNDATION_MISSION_001_AUTHORITY_DECISION.json#mission`), while this ratification covers the *Mission node generally*. The dossier's position: FM001 decided the ownership question for the mechanisms; ratification generalizes it from instance to node. An operator could disagree and require a fresh decision surface.
3. **The authorization tension (migration authored + live battery run vs. FM001's denied list).** STREAM H recorded the tension (`#cautions[LIVE-VERIFIED vs NOT APPLIED]`); the operator may want the durable-posture ruling *before* ratifying the owner, or may ratify with the condition suggested in §5.
4. **Placement**: whether ratification should be accompanied by a directive to relocate the substrate out of `frontend/src/lib/` (ties to COND-013, separately gated — `COREGRID_V1_MISSION_GRAPH.json#missions[MISSION-R-03].objective`).
5. **Candidate A's seam-argument**: co-locating Mission with Delegation/Worker in 07 would reduce one ownership seam (Mission->Delegation). If the operator weights seam-count above separation-of-powers, A becomes arguable; this dossier weighs separation-of-powers higher because the mission spine is the enforcement surface over agents (AGENTS.md §21).
