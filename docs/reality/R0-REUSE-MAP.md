**Version target:** R0 design/audit only. This is a documentation inventory, not evidence that any migration is applied or a capability is deployed. This follows the repository's [V1 scope lock](../v1/V1-SCOPE-LOCK.md) and [execution boundary](../../AGENTS.md#45-v1-execution-boundary).

## Reading the inventory

Each row maps an issue #229 domain to existing database objects, migration sources, runtime/domain modules, and focused tests. Paths below link to the repository's `master` tree. Table names are the names declared or consumed in those sources. A citation establishes that a source file exists and contains the named implementation; it does **not** establish live deployment, production verification, or complete issue acceptance.

The tags **built**, **partial**, and **missing** in [the gap matrix](R0-GAP-MATRIX-ROADMAP.md#institution-by-domain-gap-matrix) refer to the bounded building block in that cell, not completion of the full Reality Engine or scenario. **V2** is reserved for the frozen physical-device/IoT or physical-reality-intelligence overlay.

## Existing Reality Core and reuse boundary

The most direct existing Reality Core is the Scholar operating model: `publishInstitutionOperatingModel` validates a build spec, writes entity type `scholar.institution.operating_model` to `cg_entity`, versions the record with the kernel's `superseded_by`, and writes an audit event to `cg_event`. Its code is in [`scholar-institution-config.functions.ts`](https://github.com/vibeoraai-bit/coregrid-scholar-migration/blob/master/frontend/src/lib/runtime/scholar/scholar-institution-config.functions.ts). The kernel table definitions are in [`20260903000000_coregrid_universal_kernel_substrate.sql`](https://github.com/vibeoraai-bit/coregrid-scholar-migration/blob/master/database/supabase/migrations/20260903000000_coregrid_universal_kernel_substrate.sql); the Scholar vocabulary and draft adapters are in [`scholar-reality.ts`](https://github.com/vibeoraai-bit/coregrid-scholar-migration/blob/master/frontend/src/lib/runtime/scholar-reality.ts), with flow tests in [`runtime-scholar-reality.test.ts`](https://github.com/vibeoraai-bit/coregrid-scholar-migration/blob/master/tests/unit/runtime-scholar-reality.test.ts). The current publisher resolves scope through `requireSchoolAdminScope`; R1 must explicitly confirm how that identifier maps to #229's neutral organization key instead of assuming school and organization IDs are interchangeable.

The kernel primitives are generic: `cg_entity` carries entity type, tenant, attributes, classification, source, confidence and valid-time fields; `cg_relationship` has relation type, a tenant field and time-bounded edges; `cg_observation` keeps observed/reported/inferred/predicted/simulated kinds distinct; `cg_event` carries actor, tenant, idempotency and audit/event data. The source migration enables RLS and revokes direct `anon`/`authenticated` access. It does **not** declare `FORCE ROW LEVEL SECURITY` on these four tables in that migration. That is a gap to resolve in any approved follow-on, not an existing guarantee.

Use the existing owners; do not create duplicates of:

- organization/topology: `cg_org_unit`, `cg_org_membership`, and the existing institution/campus structures;
- identity and access: `cg_identity`, existing memberships, #196 role/responsibility/permission engine;
- workspaces: #207 workspace shell and its `workspace_org_units`/manifest owners;
- websites: #135 website engine and its existing site/version/audit records;
- scheduling: #227 scheduling and existing timetable/period/shift records;
- twin surfaces: #223 personal-twin and existing Scholar facility-twin contracts.

The #196 role-engine migration is [`20261101000010_sherivs_m009_a1_role_responsibility_engine.sql`](https://github.com/vibeoraai-bit/coregrid-scholar-migration/blob/master/database/supabase/migrations/20261101000010_sherivs_m009_a1_role_responsibility_engine.sql); the #207 workspace manifest source is [`20261025100210_sherivs_ux1_workspace_manifest.sql`](https://github.com/vibeoraai-bit/coregrid-scholar-migration/blob/master/database/supabase/migrations/20261025100210_sherivs_ux1_workspace_manifest.sql); the website source is [`20261025100240_sherivs_100_website_engine.sql`](https://github.com/vibeoraai-bit/coregrid-scholar-migration/blob/master/database/supabase/migrations/20261025100240_sherivs_100_website_engine.sql). These existing systems remain owners, not Reality-managed duplicates.

## R0 conclusion

There is a substantial reusable substrate and working domain code, but the citations do not establish an integrated, fully validated educational Reality Engine or any complete A–L scenario. The main R1 design question is how to evolve the current operating-model entity and Scholar ontology so they represent adaptable institutional reality, provenance, approvals and effective dates without replacing the existing domain owners. The proposed extension posture and its security gates are in [the roadmap](R0-GAP-MATRIX-ROADMAP.md#proposed-db-changes-r0-design-only).
