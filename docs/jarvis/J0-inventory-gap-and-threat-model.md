# SV1-JARVIS J0 — Inventory, gap matrix, architecture, and threat model

- **Snapshot:** 2026-11-01
- **Version target:** J0 is documentation-only analysis of the existing V1 organizational control-plane and worker substrate. This document does not claim that a JARVIS workforce is implemented, tested, or deployed.
- **Evidence boundary:** Source and repository-recorded status only; no live database, production console, provider, or deployment was accessed.

## Scope and status

Issue [#225](https://github.com/vibeoraai-bit/coregrid-scholar-migration/issues/225) requests the JARVIS workforce and sequential J0–J6 phases. The existing Control Plane V1 gap matrix explicitly lists the “AI workforce control plane” as deferred, not V1 (`progress/internal-console/CONTROL-PLANE-V1-GAP-MATRIX.md:54-58`). The repository execution boundary permits implementation only within the V1 organizational capability envelope and freezes V2, V3, and future-unassigned capabilities absent an explicit human authorization record (`AGENTS.md:923-924`).

Accordingly:

- **J0:** documented in this change; no runtime, schema, configuration, or production changes.
- **Scope update:** the owner-authorized V1 scope record in `docs/v1/V1-SCOPE-LOCK.md` names the bounded JARVIS slice from #225. That authorization supersedes this inventory's historical pending-scope statement and the older Control Plane gap-matrix classification for this named slice only.
- **J1–J6 implementation status:** authorized V1 scope is not implementation evidence. The workforce registry, durable approval inbox, connected passkey step-up, channel escalation, playbooks, and report feed remain gaps; this home-shell UI does not implement them or connect a chat backend.
- Existing V1 console, authorization, worker, trust, and incident capabilities remain reusable within their current boundaries; their presence does not authorize broader control-plane autonomy.

Do not treat the “80% autonomous” target, role agents, outbound escalation, or a JARVIS/Grok feed as implemented. Any later implementation claim must state its version-target classification and evidence separately.

## Proposed architecture boundary (design only)

Use the existing control-plane, workforce, authorization, trust, and execution boundaries. Do not add a standalone JARVIS process, parallel role engine, second twin runtime, or a direct model-to-provider action path.

```text
event / scheduled trigger
  → authenticate source; validate and classify untrusted content
  → build authorized, minimized control-plane context
      (aggregate data by default; tenant detail only through an audited support grant)
  → AI gateway proposal + provenance
  → versioned policy decision (risk tier, capability, tenant/resource, budget, kill switch)
      T0/T1 eligible for bounded autonomous action
      T2 human console approval
      T3 Sheriff passkey approval in console; never autonomous
      T4 deny in policy and enforcement layers
  → human approval resolution where required
  → short-lived, scoped executor through governed APIs
  → append-only audit/evidence and independent outcome verification
  → minimized report; optional read-only Grok feed
  → bounded worker sleeps/terminates
```

The current platform staff functions enforce authenticated requests, platform capabilities, AAL2 for privileged changes, and staff audit records (`frontend/src/lib/platform-staff/staff.functions.ts:45-60,88-105,147-155`). That is a human control-plane boundary, not permission for an AI actor. Agent authority must be identity-bound and pre-delegated; approval, executor credentials, and agent proposals must remain separate.

Before any later phase changes code, resolve these design gates:

1. Record the human version-scope decision reconciling #225 with the existing “AI workforce control plane” V1 deferral.
2. Define a platform-scoped worker/authority context that does not masquerade as a tenant or human staff identity; specify aggregate APIs and the audited support-grant path.
3. Version a fail-closed mapping from requested T0–T4 to existing agent/automation risk classes. T3 and T4 must have no autonomous execution path.
4. Persist approval requests and decisions with evidence, recommendation, rollback, expiry, independent resolver, replay/idempotency protection, and execution-time revalidation. Connect T3 approval to console passkey step-up.
5. Define channel contracts and failure behavior only after #218/#219/#222 are available. Phone acknowledgement/denial is not approval; test-mode escalation must never contact a real recipient.
6. Bind worker budget, capability, lifecycle, global/agent stop, and audit correlation to every action. Preserve separate proposals, approvals, execution receipts, verification, and append-only audit.
7. Map the five operational playbooks to the existing six workspaces without changing human role authority; keep personal Twin integration within the bounded #223 V1 authorization and its phase/security gates.

## Threat model

| Threat / trust boundary | Required control | Current evidence and remaining gap |
|---|---|---|
| Prompt injection in tickets, emails, chat, calls, or reports | Treat all external content as untrusted data; isolate instructions from evidence; validate model output and tool arguments; red-team each ingestion path. | Generic gateway defenses and tests exist. No proof that every proposed JARVIS source passes through them. |
| Agent crosses tenants or reads personal/sensitive data | Enforce identity + capability + tenant + purpose at server/RLS boundaries; aggregates by default; tenant details only with a live audited support grant. | Platform and tenant scopes are distinct in `docs/console/architecture-current.md:14-18,26-30`; no JARVIS context builder is present. Never trust a client-supplied tenant ID. |
| Agent impersonates staff, self-approves, or expands delegated authority | First-class AI identity, human-granted bounded delegation, independent human resolver, no self-approval, revocation and expiry checks. | Delegation/approval contracts enforce these properties; no console-agent identity registration or role binding exists. |
| T3 action slips through an approval, retry, or phone flow | Fail closed; console passkey step-up; bind approval to exact proposal and resource; revalidate expiry/revocation immediately before execution; phone supports acknowledge/deny only. | Generic AAL2 and approval primitives exist, but no JARVIS inbox or connected T3 execution gate. |
| Duplicate, stale, or partially completed action | Idempotency key, scoped short-lived executor, pre/postcondition checks, compensation/rollback plan, independent verification, visible unknown outcome. | Automation/action and mission contracts provide components; JARVIS proposal-to-executor orchestration is absent. |
| Credential, secret, or spending abuse | No standing agent credentials; approved scoped broker grant only; least privilege, rate/budget limits, redacted logs, provider test rails. | Credential broker and worker budget abstractions exist; no JARVIS-specific scope or budget binding. |
| Audit alteration or missing action provenance | Append-only hash-linked records; audit proposal, policy, human decision, channel attempt, execution, verification, and outcome with correlation IDs. T4 audit deletion/guardrail bypass must remain denied in code and DB. | The database audit chain has append-only triggers and RLS; there is no JARVIS event catalogue or complete cross-channel correlation path. |
| Runaway loops, queue flood, or cost exhaustion | Ephemeral bounded cycles, token/cost/action/time limits, per-agent and global stop, idempotent triggers, backpressure, operator visibility. | Worker lifecycle budgets and automation stop vocabulary exist; platform-level agent registry and operational stop persistence are gaps. |
| Spoofed call or accidental live escalation | Server-resolve and validate recipients; signed callbacks; rate limits; quiet-hour/P0 policy; test-mode drill; no approval by keypad. | Telephony contract exists; Africa’s Talking integration and JARVIS dispatch path remain draft/unmerged. |
| Grok feed becomes a write or data-exfiltration path | Authenticated read-only contract, minimized/redacted report fields, provenance, no production mutation tools or secrets. | No report feed was identified; requirement is design-only. |
